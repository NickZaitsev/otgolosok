# Запуск каталога OSM и удалённого just-tts в production

Эта инструкция относится к существующему сайту `otgolosok.softmg.tech`: backend
и постоянная база находятся на сервере сайта, `just-tts` с моделью работает на
отдельном сервере. Вся генерация текста платная. Команды создания партий ниже
ставят задания **на паузу**; запуск обработки выполняется отдельно в админке.

## 1. Подготовить релиз сайта

Убедитесь, что в релиз включены `CONTENT_AUTO_APPROVE`, транспорт `http` и
маршруты `/api/content/*`, `/api/story-admin/content/*` и `/api/auth/*`. Эти
возможности должны быть доступны в работающем backend, а не только в локальной
ветке. Следуйте [инструкции существующего деплоя](production-deployment.md):
используйте инфраструктурные цели `deploy-otgolosok-generator` и
`deploy-otgolosok-prod` из `/Users/fenix007/projects/utils/services`, выполняя
обновление backend до frontend. Не заменяйте production Compose конфигом из
корня этого репозитория. Перед обновлением сохраните согласованную резервную
копию `generator-data` (база, WAL и аудиофайлы) и production-конфигурации.
Локальный `backend/data/jobs.sqlite` не переносите поверх production-базы.

В существующий файл `/srv/sites/otgolosok.softmg.tech/.generator.env` добавьте
или проверьте значения (секреты не записывайте в Git):

```dotenv
APP_ORIGIN=https://otgolosok.softmg.tech
OPENAI_BASE_URL=https://<совместимый-Responses-API>/v1
OPENAI_API_KEY=<ключ-генерации-текста>
STORY_MODEL=<модель-исследования-и-проверки>
WRITER_MODEL=<модель-написания>
CONTENT_AUTO_APPROVE=true
CONTENT_WORKER_CONCURRENCY=1
LOCAL_TTS_TRANSPORT=http
LOCAL_TTS_ENGINE=f5
TTS_API_URL=https://<защищённый-адрес-tts>
TTS_API_TOKEN=<тот-же-токен-что-и-на-сервере-tts>
F5_MODEL_SHA256=<sha256-checkpoint>
F5_REFERENCE_ID=<идентификатор-голоса>
F5_CONFIG_SHA256=<sha256-конфигурации>
F5_REFERENCE_SHA256=<sha256-референса-при-наличии>
```

Для Silero вместо `f5` выберите `LOCAL_TTS_ENGINE=silero` и согласуйте
`SILERO_MODEL_SHA256` и `SILERO_SPEAKER` с профилем `just-tts`. Настройки TTS
копируются в задания при создании: смена движка после этого не изменит профиль
уже созданных партий. Настройки окружения требуют пересоздания backend
контейнера; проверьте, что production Compose действительно передаёт все эти
поля. Проверка `docker compose config` полезна, но может раскрыть секреты:
не публикуйте её вывод.

Production reverse proxy должен отправлять `/api/content/*`,
`/api/story-admin/*`, `/api/auth/*` и остальные используемые приложением API
на backend, включая `HEAD` и `Range` для `/api/story-audio/*`. По старой
документации маршрутизируются лишь `/api/story-*` и маршруты прогулок; эту
конфигурацию необходимо проверить и обновить до публикации frontend.

## 2. Поднять just-tts на другом сервере

Используйте инструкцию `docs/deployment-linux.md` из отдельного репозитория
`just-tts` (`C:\00_projects\just-tts` на локальной машине)
на машине с NVIDIA GPU для F5: установите Docker/NVIDIA runtime, перенесите
подготовленный F5-контекст, создайте локальный `.env` с `TTS_API_TOKEN`,
`TTS_ENGINE=f5`, `WORKER_DEVICE=cuda` и настройками модели. Затем выполните
`docker compose build --pull` и `docker compose up -d`. Для Silero выберите
совместимую модель и соответствующую настройку контейнера; текущий Compose
`just-tts` содержит `gpus: all` и рассчитан на GPU.

Проверьте на машине TTS `GET /healthz` и авторизованный `GET /v1/profiles`.
Сверьте профиль, модель, голос, конфигурацию и версию подготовки текста с
переменными сайта. Для двух серверов откройте только защищённый HTTPS endpoint
TTS, разрешите доступ только backend сайта; токен никогда не отдавайте браузеру.
Отправьте короткое тестовое задание, получите MP3, прослушайте и подтвердите
приём (`ack`) согласно `docs/http-api-v1.md` из репозитория `just-tts`.
Backend сайта сам ставит задания TTS, скачивает MP3 и сохраняет файл в своём
постоянном `generator-data/audio`.

## 3. Импортировать достопримечательности в существующую базу

Подготовленный снимок `backend/data/osm-attractions.json` содержит 6 107
отобранных объектов в административных границах Москвы. Он локальный и не
входит в Git или Docker-образ: отдельно перенесите именно этот JSON на сервер
сайта и проверьте `coverage=moscow-admin`, checksum исходного PBF и границы.
При необходимости новый снимок можно получить скриптом
`scripts/import-osm-attractions.py` из PBF и проверенного GeoJSON границы;
команда и параметры приведены в [README](../README.md).

Загрузите его с checkout того же релиза и Node.js версии из `package.json`,
указав `DATA_DIR` на **тот же постоянный том**, который смонтирован в
работающем backend как `/data`. В production имя `generator-data` может быть
Docker volume, а не каталог хоста: сначала проверьте фактический mount через
`docker inspect` контейнера backend. Используйте отдельный одноразовый
контейнер с этим томом и исходниками скриптов, если это named volume;
в текущем backend-образе скриптов нет. Следующая команда предназначена только
для случая, когда `generator-data` — именно bind mount доступного с хоста
каталога. Замените путь к файлу и каталогу на проверенные абсолютные пути.
Для импорта полного снимка поставьте активные партии на паузу; загрузите
каталог из checkout без запуска второй копии backend:

```bash
export DATA_DIR=/srv/sites/otgolosok.softmg.tech/generator-data
node scripts/load-osm-catalog.mjs /srv/sites/otgolosok.softmg.tech/osm-attractions.json --complete
```

`--complete` архивирует объекты, которых нет в загружаемом полном снимке;
применяйте его только после бэкапа и сверки границ. Не запускайте второй
backend на той же SQLite базе. Убедитесь через админку
`/admin?section=content`, что каталог появился и число объектов ожидаемое.

## 4. Создать задания и запускать партиями

На том же checkout, с тем же `DATA_DIR` и `LOCAL_TTS_ENGINE` (для F5 также
`F5_MODEL_SHA256`, `F5_REFERENCE_ID`, `F5_CONFIG_SHA256`), создайте первую
небольшую партию, чтобы проверить всё до платного массового запуска:

```bash
node scripts/create-osm-batch.mjs --next --limit 10
```

После проверки в `/admin?section=content` возобновите эту партию. Дождитесь
текстов и MP3, убедитесь, что опубликованные карточки читаются через
`/api/content/places?status=ready`, а аудио воспроизводится на сайте. Изучите
затраты токенов и число отказов. Затем повторяйте команду с посильным размером
партии (максимум 5 000); `--next` пропускает объекты, для которых уже есть
задание `story-v1`, и при исчерпании каталога завершится сообщением, что
доступных объектов больше нет. Каждая партия по умолчанию создаётся на паузе;
запускайте их из админки, наблюдая очередь и расход. Не используйте `--start`,
пока не проверены объём партии и выбранный TTS-профиль.

`CONTENT_AUTO_APPROVE=true` действует только на **новые успешно законченные**
текстовые задания: прошедший автоматическую проверку текст публикуется сразу,
а в партии `text-and-audio` для него создаётся задание TTS. Флаг не исправляет
`failed`, `review_required`, `insufficient_evidence` и не публикует задним
числом старые черновики. Для них нужны разбор причин и отдельные повторы;
скрипт `--next` не повторяет уже созданные задания. Текст может появиться на
сайте раньше аудио; MP3 публикуется после загрузки и проверки сервером.
Автоматическая проверка не заменяет человеческой оценки фактов и произношения:
реальный пилот дал 7 принятых текстов из 50. Проверяйте выборку перед ростом
объёма и не считайте число поставленных заданий числом опубликованных историй.

Переход на автоматическое утверждение создаёт риск публикации текста с ошибками
даже после успешной модельной проверки. Правильное снижение этого риска —
редакторская выборка и исправление обнаруженных ошибок до следующей партии;
при неприемлемом качестве верните `CONTENT_AUTO_APPROVE=false` для новых работ.

При остановке генерации поставьте все активные партии на паузу в админке:
уже запущенные запросы могут успеть завершиться. Проверьте число готовых,
ожидающих и отклонённых заданий и состояние TTS-очереди. Если TTS временно
недоступен, опубликованный текст остаётся доступен; после восстановления
сервиса проверьте просроченные задания и при необходимости повторите их
через админку.
