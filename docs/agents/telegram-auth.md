# Регистрация и вход через Telegram

## Поведение

Кнопка «Продолжить через Telegram» доступна и на входе, и на регистрации. Первый
вход создаёт пользователя, последующие находят тот же аккаунт по проверенному
OIDC `sub`. Имя и username не участвуют в идентификации. Аккаунт с почтой и
Telegram-аккаунт одного человека остаются отдельными, автоматического объединения
нет. Email-вход сохраняет прежнее поведение.

Реализация использует [современный Telegram OIDC](https://core.telegram.org/bots/telegram-login)
и стандартные маршруты Better Auth 1.7.5. Браузер переходит на Telegram целиком,
без внешнего JS и всплывающего окна. При сетевом сбое доступна повторная попытка,
поля email-формы сохраняются. Ожидание отложенного выхода после офлайна исключает
поздний отзыв только что созданной сессии.

## Настройка

1. В мини-приложении [BotFather](https://t.me/BotFather) выберите бота → **Login Widget**.
2. Добавьте Allowed URLs: `https://otgolosok.online` и
   `https://otgolosok.online/api/auth/callback/telegram`. Для другой среды подставьте
   точный `APP_ORIGIN`; callback всегда `${APP_ORIGIN}/api/auth/callback/telegram`.
3. В Login Widget → Advanced оставьте **RS256**.
4. Полученные Client ID и Client Secret задайте только на backend:
   `TELEGRAM_LOGIN_CLIENT_ID` и `TELEGRAM_LOGIN_CLIENT_SECRET`. Это отдельные
   OAuth-реквизиты, токен Bot API не подходит. Секрет не передаётся frontend.
5. Перезапустите backend. `GET /api/auth/providers` должен вернуть
   `{ "telegram": true }`; затем выполните проверку реального входа.

Оба значения отсутствуют или пустые — провайдер выключен, endpoint возвращает
`false`, кнопка скрыта. Частично заполненная пара или нечисловой Client ID
останавливает запуск с безопасной ошибкой конфигурации. Статус показывает наличие
конфигурации, а не доступность Telegram по сети. При старте внешних запросов нет.

## Проверка личности и хранение

Запрашиваются только `openid profile`. Телефон и разрешение боту писать не
запрашиваются. Authorization Code Flow использует PKCE S256, одноразовый `state`
и серверный `nonce`. Прямой вход с присланным браузером ID token отключён.
При первом запуске OAuth обязательны точный Origin сайта и отсутствие
`Sec-Fetch-Site: cross-site`, даже когда сессионного cookie ещё нет.

Провайдер проверяет подпись RS256 через закреплённый Telegram JWKS endpoint,
issuer, audience, срок и возраст токена, `sub` и совпадение nonce. Адреса Telegram
закреплены в коде, redirect внешних HTTP-запросов запрещён. Timeout — 5 секунд;
сетевые ошибки, 429 и 5xx имеют до трёх попыток с ограниченной экспоненциальной
паузой. Детерминированные 4xx не повторяются. Ответ token endpoint ограничен
64 КиБ при потоковом чтении; ошибки не включают токены и secret.

Better Auth требует email, поэтому внутри базы хранится стабильный
`sha256(sub)@users.telegram.invalid` с `emailVerified=false`. Весь домен
`users.telegram.invalid` запрещён для регистрации через пароль и иных источников.
Публичные `/api/auth/session` и `/api/me` возвращают `email: null`,
`authMethod: "telegram"` и `requiresReauthentication`. UI показывает «Telegram».
OAuth-токены в `account` шифруются Better Auth. Связь идентичности хранится
только в `account(providerId, accountId, userId)`; отдельного поля в user нет.
Частичный уникальный индекс защищает пару provider/accountId для Telegram.

Миграция Better Auth добавляет `session.authProvider`, доступный только backend.
Он выставляется в callback Telegram после проверок и не принимается из формы.
У прежних сессий маркера нет, это требует повторного входа перед удалением.

При двух одновременно пришедших первых callback одной личности база сохраняет
одного владельца; одна попытка может получить стандартную ошибку создания
пользователя Better Auth. Повторный вход безопасно открывает уже созданный аккаунт.
Тест проверяет отсутствие лишних пользователей и связей.

## Удаление аккаунта

Email-аккаунт по-прежнему требует пароль. Telegram-аккаунт допускает пустое тело
DELETE только при реальной единственной Telegram-связи аккаунта, совпадении
внутреннего email с её subject, маркере Telegram у сессии и её возрасте не более
пяти минут от неизменяемого `createdAt`. CSRF и same-origin проверки обязательны.
Обновление `expiresAt` не продлевает окно подтверждения. Старые сессии получают
`403 REAUTH_REQUIRED`.

UI возвращает пользователя в Telegram, затем открывает подтверждение удаления.
Ничего не удаляется автоматически после callback. Идентификатор ожидаемого
пользователя сохранён в sessionStorage; если вошёл другой аккаунт, удаление
отменяется. Если окно свежести истекло на открытой странице, отказ сервера сразу
переключает кнопку на повторный вход. Удаление каскадно отзывает сессии и данные
аккаунта, включая доступ к незавершённым исследованиям.

## Проверки и включение на production

Локальные тесты используют собственные RSA-ключи и имитацию HTTP-ответов Telegram.
Они проверяют криптографические отказы, CSRF, одноразовый state, PKCE/nonce,
зарезервированный email, повторный вход, конкурентную регистрацию, отсутствие
автосвязи с email, шифрование токенов и свежее/просроченное удаление. Тесты UI
проверяют отключённый провайдер, ошибки, локали, returnTo, отложенный logout и
подтверждение удаления с другим пользователем.

Перед включением сделать резервную копию `auth.sqlite`, настроить Allowed URLs
и реквизиты, затем в приватном браузере проверить новую регистрацию, повторный
вход в того же пользователя, выход, сохранение прогулки и reauth/delete. Проверить
вход из Android-оболочки отдельно: native SDK в эту реализацию не входит.
Реальный обмен с Telegram не подтверждён до настройки BotFather и секретов.
Для отключения убрать обе Telegram-переменные и перезапустить backend: данные
Telegram-пользователей сохранятся, но войти они смогут после повторного включения.
