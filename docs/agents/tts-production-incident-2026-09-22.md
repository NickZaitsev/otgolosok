# Сбой синтеза F5 на production, 22 сентября 2026 года

Проверка выполнена из работающего production-контейнера примерно в 10:34–10:36
МСК (07:34–07:36 UTC). Backend здоров, перезапусков с момента его запуска нет;
на диске сервера сайта свободно около 14 ГБ.

Используется F5 через HTTP, профиль `f5-ru-v1`. `/v1/profiles`, `/healthz` и
`/readyz` TTS-сервера вернули HTTP 200. Хеши модели, конфигурации и референса
совпали с настройками backend. При этом успешные readiness-ответы не подтверждают
работоспособность синтеза при этом сбое.

В `external_audio_jobs`: 430 успешных и 10 завершившихся ошибкой заданий,
ожидающих и выполняющихся нет. Все 10 ошибок имеют код `SYNTHESIS_FAILED` после
трёх попыток; за последние сутки зафиксировано 30 неуспешных попыток синтеза.
Последний успех — 22 сентября в 03:47:30 МСК. Первое из неудачных заданий создано
в 04:56:29 и окончательно завершилось ошибкой в 04:59:40 МСК.

Отдельный короткий диагностический запрос отправлен тем же клиентом из
production-контейнера, без создания задания в базе сайта и без публикации.
TTS-сервер принял задание `c263a88c-c335-4700-95b0-f7b9c161b750` в 10:36:20 МСК,
затем вернул `failed/SYNTHESIS_FAILED`; проверка заняла около 16 секунд.
Аудиофайл не получен. Запись диагностического задания осталась на TTS-сервере.

Последний готовый MP3 сайта успешно отдал диапазон байтов: HTTP 206,
`audio/mpeg`, 1024 байта. Ошибка относится к получению нового аудио от TTS,
а не к отдаче уже опубликованных файлов. Генерация текстов продолжалась.

Причина внутри исполнителя F5 по публичному коду ошибки не установлена:
логи TTS-хоста в этой проверке не читались. Следующий шаг — проверить журнал
исполнителя по диагностическому ID, устранить причину и повторить короткий синтез.
После успешной проверки повторить 10 неудачных аудиозаданий штатно через админку;
автоматических попыток у них больше нет. При диагностике задания не перезапускались,
контейнеры и настройки не менялись.

## Причина и восстановление, 10:41–10:48 МСК

Доступ к TTS-хосту указан в локальном `TTS_VPS`; Compose-проект расположен в
`/opt/just-tts-private`, контейнер — `just-tts-private-tts-1`. На хосте
`nvidia-smi` исправно видел RTX 4060 Ti, свободной оперативной памяти и диска
было достаточно. В контейнере тот же вызов вернул
`Failed to initialize NVML: Unknown Error`; проверка через `/usr/bin/python3.12`
показала `torch.cuda.is_available() == False`, ноль устройств и
`RuntimeError: No CUDA GPUs are available` при выделении тензора. Именно этот
Python используется для F5; системный `python3` контейнера не содержит PyTorch.

Docker использовал `runc` 1.1.12, `systemd` cgroups v2 и legacy NVIDIA GPU
device request без явных устройств/CDI. В журнале хоста есть `systemd Reloading`
в 03:57:04 и 03:57:07 МСК, между последним успешным синтезом и первой ошибкой.
Это соответствует [известной проблеме NVIDIA](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/troubleshooting.html#containers-losing-access-to-gpus-with-error-failed-to-initialize-nvml-unknown-error):
перезагрузка unit-конфигурации может отозвать доступ к GPU у legacy-контейнера.
Точный момент отзыва доступа отдельно не зафиксирован.

Перед восстановлением проверено отсутствие `queued/running` на TTS-сервере,
снята согласованная SQLite-копия с правами `0600`:
`/var/backups/just-tts/20260922T074605Z/api.sqlite`. Только сервис `tts`
пересоздан через `docker compose up -d --no-deps --no-build --force-recreate
--wait --wait-timeout 180 tts`. Том `/data`, модель, конфигурация и окружение
сохранены; остальные сервисы и Docker daemon не перезапускались.

После восстановления `nvidia-smi` внутри контейнера заработал, PyTorch увидел
одно CUDA-устройство и успешно выделил GPU-тензор. Повторный запрос из backend
production принят в 10:47:13 МСК, ID `238a9977-f7ee-40fa-92bd-5e9c861951e0`.
За 30,5 секунды получен `succeeded`, скачан MP3 размером 59 949 байт; SHA-256
совпал, полное декодирование FFmpeg завершилось без ошибок. Диагностический
результат подтверждён через ack и удалён TTS-сервером, на сайте не публиковался.

Пересоздание восстановило сервис, но не устранило риск повторения инфраструктурного
сбоя. Нужна отдельная проверенная миграция на поддерживаемый runtime/CDI либо
явное подключение GPU-устройств по рекомендациям NVIDIA. На общем GPU-хосте
такое изменение требует проверки совместимости остальных сервисов.

Выявлена отдельная причина ложного состояния healthy: `/readyz` в
`just_tts/api.py` безусловно возвращает `ready`, а Docker healthcheck вызывает
статический `/healthz`. Следует проверять доступность CUDA и состояние исполнителя
в readiness, не запускать полный синтез на каждый probe. Эти изменения кода
и инфраструктуры в рамках восстановления не выполнялись; 10 терминальных
аудиозаданий сайта автоматически не перезапускались.
