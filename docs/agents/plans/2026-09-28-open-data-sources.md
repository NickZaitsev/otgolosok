## Контекст

Разбор наборов — `docs/agents/data-mos-open-data.md`. Два набора data.mos.ru дают факты о самом
объекте (автор, год, материал, надпись, описание) для мест, по которым поиск ничего не находит:

- 2801 «Мемориальные доски города Москвы» — 1 719 записей, совпало 647 точек каталога (с проверкой
  инициалов: 557 сходятся, 10 расходятся, 11 не с чем сравнить, 69 без инициалов в OSM);
- 60869 «Скульптуры под открытым небом» (учреждения Департамента культуры) — 699 записей, совпало 60 точек.

Около 590 совпавших мест сейчас без текста (уровни `enrich`/`manual`). Пример: «Мишка с мячом»
остановлен в пилоте enrich с `INSUFFICIENT_EVIDENCE`, а в наборе 60869 есть автор (Воробьева),
год (2008), материал (известняк) и описание.

**Цель:** строка набора, совпавшая с местом, становится ещё одним источником конвейера, наравне
со страницами из поиска. Факты по-прежнему берутся только точной цитатой, проверка текста не меняется.

## Фаза 0. Установленные факты (28.09.2026)

**API data.mos.ru** (подробно в `docs/agents/data-mos-open-data.md`):

- `https://apidata.mos.ru/v1`, ключ в параметре `api_key` (локально `DATA_MOS_API_KEY` в `.env`,
  в production ключа нет и не нужно);
- `/datasets/{id}` — метаданные, `VersionNumber`, `VersionDate`, `Columns`;
- `/datasets/{id}/rows?$top=500&$skip=N` — `[{global_id, Number, Cells:{…}}]`, **без геоданных**;
- `/datasets/{id}/features?$top=500&$skip=N` — GeoJSON, атрибуты в `properties.attributes`,
  связь со строкой по `global_id`. Без `$top` отдаёт только первые 1 000.
- Поля 2801: `Name, Text, Location, LocationInfo, InstallationDate, InstallationComment, Form, Details,
  Material, Authors[{AuthorsName, Profession}]`. Поля 60869: `SculpName, Author, ManufactYear,
  Material, Description, LocationPlace, Latitude_WGS84, Longitude_WGS84`.
- Значения «не установлен», «не установлена» и пустые строки означают «нет данных».

**Условия использования не подтверждены в первоисточнике** (`apidata.mos.ru/Home/Terms` → 500).
По вторичным источникам использование разрешено, в том числе коммерческое, со ссылкой на портал.

**Конвейер** (`backend/content-pipeline.mjs`, `runContentJob`):

- поиск: `researchPrompt` → `sourcesFrom(research)`; если источников нет, выбрасывается
  `INSUFFICIENT_EVIDENCE` (до загрузки страниц);
- загрузка: каждая страница → `{id:"s<N>", url, title, publisher, text}` и сохраняется в `checkpoint.sources`;
- факты: `validateFacts` принимает цитату, только если она найдена в `source.text`
  (`comparable(source.text).includes(comparable(quote))`, 18–500 символов);
- для `weak_identity` — `restrictWeakIdentityEvidence`: факт идентичности об объекте, цитата которого
  проходит `quoteNamesPlace`, плюс хотя бы один факт `content` об объекте.

**Источники доходят до слушателя**: `evidence.sources` → `sources: [{id,title,url,publisher}]`
в `src/features/walks/model.ts:12`, их учитывает `src/features/explore/nearby-stories.ts`.
Показываются ли ссылки на экране, проверить в фазе 4 (от этого зависит атрибуция портала).

**Образцы кода:**

- офлайн-скрипт над production-базой с `--dry-run` и сводкой JSON — `scripts/assess-identity-candidates.mjs`;
- полная замена таблицы результатов в одной транзакции — `replaceIdentityCandidates`
  (`backend/content-store.mjs:236`);
- таблица с версией правил и `content_hash` — `place_identity_candidates` (`content-store.mjs:82`);
- расстояние и нормализация названий — `identityNameKey`, `quoteNamesPlace` (`backend/identity-triage.mjs`).

Команды проверки: `npm run lint`, `npm run typecheck`, `npm test`, перед коммитом `npm run check`.

### Запреты для всех фаз

- Не встраивать запросы к data.mos.ru в конвейер генерации: данные берутся из локальной таблицы,
  которую наполняет офлайн-скрипт. Ключ API в production не нужен.
- Не принимать факты из набора без цитаты: строка набора — такой же источник, как страница.
- Не повышать `EDITORIAL_EVIDENCE_VERSION`.
- Не менять `assessPlaceEligibility` и уровни триажа в этом плане.
- Не публиковать тексты на основе наборов, пока условия использования не подтверждены (фаза 4).
- Не запускать партии на production без явного подтверждения пользователя.

## Фаза 1. Сопоставление и хранение

**Что сделать.**

1. Модуль `backend/open-data.mjs` с чистыми функциями без сети:
   - `normalizeOpenDataRecord(datasetId, row, feature)` → `{datasetId, recordId: global_id, name,
     location:{lat,lon}|null, fields}`; значения «не установлен»/«не установлена»/пустые удаляются;
   - `matchPlaque(record, places)` — точки `historic=memorial` не дальше 80 м, у которых **все** значимые
     слова названия (длиной от 4 букв, кроме «мемориальная», «доска», «памятная») по основе встречаются в
     `Name` или `Text`. Если в названии есть инициалы («В. М.»), они должны совпасть с первыми буквами
     имени и отчества после фамилии в `Name`. Больше одного кандидата — совпадения нет;
   - `matchSculpture(record, places)` — точки `tourism=artwork` или `historic=memorial` с тем же
     нормализованным названием (без кавычек и префиксов «памятник», «скульптура», «композиция») не
     дальше 1 500 м. Больше одного кандидата — совпадения нет (однофамильцы «Сон», «Ленин»);
   - `renderOpenDataSource(record)` → текст источника по-русски, одно поле — одно предложение:
     «Мемориальная доска Клечковскому Всеволоду Маврикиевичу. Надпись: «…». Место установки: улица
     Прянишникова, дом 6. Дата установки: 06.06.1978. Авторы: Смирнов С. И. (архитектор), Шакаров Г. А.
     (скульптор). Материал: …». Пустые поля пропускаются.
2. Таблица `place_open_data (place_id PRIMARY KEY, dataset_id, record_id, dataset_version, match_json,
   record_json, content_hash, imported_at)` в `content-store.mjs` по образцу `place_identity_candidates`.
   Методы `replaceOpenDataMatches(matches, {datasetId})` (замена записей одного набора в одной транзакции)
   и `getOpenDataSource(placeId)` → запись или `null`. Устаревшей считается запись, у которой
   `content_hash` не совпадает с текущим хешем места.
3. Скрипт `scripts/import-open-data.mjs`:
   - `--fetch <datasetId> --out <file>` — выгрузка набора (rows + features, пагинация по 500, повтор
     5xx/429 с экспоненциальной задержкой, до 3 попыток; 4xx — ошибка). Ключ из `DATA_MOS_API_KEY`,
     в логах и ошибках ключ не выводится;
   - `--apply <file> [--dry-run]` — сопоставление с `places` в `DATA_DIR/jobs.sqlite` и запись
     в `place_open_data`; сводка JSON: записей, совпадений, неоднозначных, по уровням триажа.
   Выгрузка запускается локально, файл копируется на сервер, `--apply` выполняется в контейнере генератора.
   Так ключ не попадает в production.
4. Выгруженные файлы — в `.gitignore` (например, `open-data/`).

**Реализация (28.09.2026).** Отличия от текста выше:

- Утилита лежит в `backend/import-open-data.mjs`, а не в `scripts/`: образ генератора копирует только
  `backend/*.mjs` (`backend/Dockerfile`), на хосте Node нет. На сервере:
  `docker exec otgolosok-generator-generator-1 node import-open-data.mjs --apply /data/open-data/2801.json`.
- Ключ таблицы — `(place_id, dataset_id)`: место может совпасть с записями двух наборов.
  Метод — `getOpenDataSources(placeId)` и возвращает массив.
- Пробный прогон на снимке каталога (6 107 мест): доски 2801 (версия 3.86 от 01.04.2026) — 607 совпадений,
  38 неоднозначных записей; скульптуры 60869 — 53 совпадения, 5 неоднозначных записей, 2 места с двумя записями.
  Меньше, чем в разборе (647 и 60), из-за проверки инициалов и отказа при неоднозначности.

**Проверка (таблично, `backend/open-data.test.mjs`).**

| Случай | Ожидание |
|---|---|
| «В. М. Клечковскому» в 13 м от доски «…Клечковскому Всеволоду Маврикиевичу» | совпадение |
| та же доска, точка в 120 м | нет |
| «Н. Ф. Григоренко» рядом с доской «…Григоренко Петру Григорьевичу» | нет (инициалы не совпадают) |
| «В. М. Клечковскому» рядом с доской без имени и отчества в `Name` | совпадение по фамилии (инициалы не с чем сравнить) |
| две точки-кандидата у одной доски | нет |
| «Мишка с мячом» в 430 м от «„Мишка с мячом“» | совпадение |
| два «Ленина» в радиусе 1 500 м | нет |
| поле «не установлен» | нет в `fields` и в тексте источника |
| `renderOpenDataSource` | цитата «Шакаров Г. А.» находится в тексте |

- Тест хранилища: `replaceOpenDataMatches` одного набора не трогает записи другого; устаревшая запись
  не возвращается `getOpenDataSource`.
- Тест скрипта: ответ 500, затем 200 → выгрузка завершена; 401 → ошибка без ключа в сообщении.

## Фаза 2. Источник в конвейере

**Что сделать.**

1. `runContentJob` на шаге загрузки источников: если `store.getOpenDataSource(job.place.id)` вернул
   запись, первым в `checkpoint.sources` добавить `{id:"d1", url:"https://data.mos.ru/opendata/<datasetId>",
   title:"<название набора> — <имя записи>", publisher:"data.mos.ru", text: renderOpenDataSource(record),
   openData:{datasetId, recordId, datasetVersion}}`.
2. Если поиск не нашёл источников, но запись набора есть, задание не падает с `INSUFFICIENT_EVIDENCE`
   до шага фактов, а продолжает работу с одним источником `d1`.
3. `factsPrompt`: для источника с `openData` одна строка правила — это официальная запись открытых
   данных Москвы, которую приложение сопоставило с этим объектом OSM по названию и расстоянию. Она может
   подтверждать идентичность, если её название совпадает с объектом. Остальные правила промпта не меняются.
4. Повтор старых остановленных заданий с `restartFrom:"auto"` должен подхватить источник:
   `checkpoint.sources` уже сохранены. Поэтому при `restartFrom:"auto"` и наличии записи набора, которой
   ещё нет среди `checkpoint.sources`, источник `d1` добавляется, а `evidence` и последующие шаги сбрасываются.

**Проверка.**

- Тест `runContentJob`: запись набора + пустой поиск → `ready`, в evidence есть факт с `sourceId:"d1"`.
- Тест: запись набора + обычные источники → `d1` первый, `s1…` сохранены.
- Тест: `weak_identity`, цитата идентичности из `d1` («Мемориальная доска Клечковскому…») проходит
  `quoteNamesPlace` для «В. М. Клечковскому».
- Тест: задание, остановленное до импорта, после `retryBatchItem(..., {restartFrom:"auto"})` получает `d1`.
- Тест: места без записи набора работают как до изменения (существующие тесты без правок).

## Риски

- Ложное сопоставление даст текст о другом объекте. Защита: строгие правила, отказ при
  неоднозначности, модель сама подтверждает идентичность, проверка текста, публикация после утверждения.
- Записи с пустыми полями подтверждают объект, но фактов не дают. Такие места останутся
  `INSUFFICIENT_EVIDENCE`, это ожидаемо.
- Наборы обновляются (у 60869 версия 1.16 от 05.09.2025). Повторный `--fetch`/`--apply` заменяет записи;
  уже готовые тексты не пересчитываются автоматически.
- Связь с планом ансамблей (`2026-09-28-ensemble-context.md`): «Мишка с мячом» может пройти здесь фактами
  об объекте без правила ансамбля. Планы независимы, порядок выполнения выбирает пользователь.
