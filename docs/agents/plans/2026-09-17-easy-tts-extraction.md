# Перенос TTS-воркера в just-tts

Статус: план реализации. Сам перенос ещё не выполнен.

## Результат

Создать самостоятельный локальный Git-репозиторий
`C:\00_projects\just-tts` рядом с `otgolosok`. Его можно скопировать или
клонировать на другую машину и запускать без исходников сайта и Node.js.
Публикация репозитория и push — отдельный шаг после выбора remote.

Два режима используют один пайплайн:

- `speak`: текст или UTF-8 файл → нормализация → ударения → Silero → WAV.
- `worker`: получить задание → тот же синтез → загрузить WAV → ждать задание.

Первая версия: один процесс, одно задание за раз, Silero v5.5, голос `baya`,
CPU по умолчанию, GPU через настройку устройства. Модель, нормализатор и
акцентор загружаются один раз на процесс. Собственная БД, брокер очередей,
HTTP-сервер и обязательный Docker не нужны.

## Граница между репозиториями

В `just-tts` переходят синтез, подготовка текста для модели, разбиение длинного
текста, склейка WAV, HTTP-клиент, heartbeat, повторы запросов, spool и Python-тесты.
Существующий F5 command adapter сохраняется как необязательная возможность;
новые движки и систему плагинов в перенос не включать. Mock остаётся для тестов
и включается только явно; обычный запуск использует Silero.

В `otgolosok` остаются очередь, профили, токены, версии текстов, lease,
проверка загруженного аудио, нормализация громкости, MP3, хранение и публикация.
Backend уже нормализует текст перед созданием `spokenText`, а воркер повторно
готовит его для Silero. При переносе сохранить этот порядок и текущие версии
профиля; изменение нормализации требует отдельного решения и сравнения качества.

Связь — существующий `/api/worker/v1` по исходящим HTTPS-запросам воркера.
Входящие порты на его машине не требуются. Репозитории не зависят от соседнего
каталога, submodule, symlink или общей Python-библиотеки.

## Минимальная структура just-tts

```text
just-tts/
  pyproject.toml
  README.md
  .env.example
  .gitignore
  just_tts/
    __init__.py
    __main__.py       # speak, worker, download-model
    config.py        # CLI, env, явный --env-file, пути
    synthesis.py     # подготовка текста, модель, WAV
    worker.py        # API, lease, heartbeat, spool
  tests/
  examples/
    sample.txt
  docs/
    worker-api-v1.md
  .github/workflows/
    tests.yml
```

Модель, `.venv`, `.env`, spool и сгенерированное аудио исключить из Git.
`pyproject.toml` — единый источник Python-зависимостей; PyTorch устанавливается
отдельно для CPU или выбранной CUDA. Начать с Python 3.12 и текущих
`ru-normalizr==0.3.0`, `silero-stress==1.5`; совместимую версию PyTorch подтвердить
установкой в чистое окружение. FFmpeg устанавливается как системная зависимость.

## Шаги реализации

### 1. Зафиксировать исходное поведение и контракт

- Запустить текущие Python-тесты и проверки backend для внешнего аудио.
- Описать в `docs/worker-api-v1.md` методы `claim`, `heartbeat`, `fail`, `result`
  и чтение состояния задания; поля профиля и задания, HTTP-коды, заголовки
  авторизации, lease, SHA-256 и upload ID. Использовать обезличенные примеры.
- Сохранить профиль `silero-ru-v1`, checksum модели, `baya` и WAV 48 kHz.
  Версия пакета воркера независима от версии HTTP API и TTS-профиля.
- Зафиксировать исходный commit `otgolosok` в документации нового репозитория.
  Перенести выбранные файлы новым начальным коммитом, без всей истории сайта.

### 2. Перенести код и убрать зависимости от дерева сайта

- Перенести `workers/tts/worker.py`, `generate_sample.py`, зависимости и тесты;
  выделить общую функцию синтеза, которую вызывают оба режима.
- Заменить `parents[2]/backend/data/models/...` на путь в каталоге данных
  `just-tts`. По умолчанию использовать `~/.just-tts`, с настройкой
  `JUST_TTS_HOME`; отдельные пути модели и spool также можно переопределить.
  Пути spool хранить абсолютными, чтобы перезапуск из другого cwd был безопасен.
- Добавить `download-model`: официальный URL Silero v5.5, временный файл,
  проверка SHA-256 и переименование только после успешной проверки.
  Уже проверенную модель повторно не скачивать. Действующую локальную модель
  можно скопировать или явно указать через `SILERO_MODEL_PATH`.
- Заменить зависимый от схемы сайта `--route/--poi/--paragraph` на `--text-file`.
  Текст для примера положить в `examples/sample.txt`; маршруты остаются у сайта.
  Сравнение всех голосов и опциональный `--loudnorm` сохранить в локальном режиме.
- Заменить Windows-специфичный `NUL` на переносимый null output FFmpeg.
  В режиме worker отправлять исходный WAV: громкость и MP3 обрабатывает backend.
- Перенести существующие тесты, проверить импорты установленного пакета.
  Уже записанные `artifacts/tts-*` оставить в `otgolosok` как исторические образцы.

### 3. Сделать установку и запуск понятными

Предлагаемый интерфейс после реализации:

```text
just-tts download-model
just-tts speak --text "Проверка голоса." --output sample.wav
just-tts speak --text-file examples/sample.txt --output sample.wav
just-tts --env-file .env worker
just-tts --env-file .env worker --once
```

- Описать создание venv, установку PyTorch, `pip install .`, FFmpeg,
  загрузку модели и запуск отдельно для PowerShell и Linux shell.
- Сохранить существующие `WORKER_*`, `SILERO_*`, `TTS_ENGINE`, `F5_TTS_COMMAND`.
  Приоритет: аргументы CLI → окружение процесса → явно выбранный env-файл →
  значения по умолчанию. Для env-файла использовать готовый небольшой парсер.
- Минимальные настройки подключения: `WORKER_API_URL` и `WORKER_TOKEN`;
  `WORKER_ID` по умолчанию — hostname, профиль — `silero-ru-v1`.
  Показать получение отдельного токена в админке сайта.
- Проверять настройки до загрузки тяжёлых моделей; локальный `speak`
  не требует токена и адреса backend. Первый запуск может требовать интернет
  также для ресурсов нормализатора и акцентора; указать это в инструкции.
- Выводить понятные сообщения: ожидание, задание, синтез, отправка, ошибка.
  Секреты и полные тексты заданий в обычные логи не включать.

### 4. Проверить надёжность и совместимость

Сохранить retries с backoff, проверку профиля, lease и идемпотентную отправку.
Проверить сценарии, критичные для отдельного длительно работающего процесса:

- Пустая очередь возвращает ожидание; `--once` корректно завершает процесс.
- Ошибка синтеза отправляется в `fail`; 401/403 видны оператору и не скрываются
  бесконечным ожиданием. Несовместимые профиль, модель и голос отклоняются.
- Heartbeat действует во время подготовки, синтеза и загрузки. Потеря lease
  исключает отправку устаревшего результата. В текущем коде heartbeat завершается
  перед upload — покрыть длительную загрузку и устранить этот разрыв.
- Завершённый WAV переживает перезапуск; повторная отправка использует прежний
  upload ID. Частичный файл после прерывания синтеза не считается завершённым.
  Отдельно проверить просроченный lease и новую lease generation.
- Локальные тесты HTTP-клиента используют небольшой тестовый сервер и не требуют
  PyTorch, модели или checkout `otgolosok`. CI запускает их на Windows и Linux.
- Проверить реальный Silero на CPU: короткий и длинный тексты, числа и сокращения,
  корректный WAV и прослушивание примера. CUDA проверяется отдельно при наличии GPU.
- Сквозной тест с локальным backend: claim → heartbeat → WAV → публикация MP3.
  Для mock использовать отдельный тестовый профиль `engine=mock` в fixture;
  текущий production-профиль `silero-ru-v1` проверяет движок и для mock не подходит.
  Проверить также один полный проход с Silero и выданным тестовым токеном.

### 5. Переключить otgolosok на внешний воркер

- Сначала завершить проверки и создать коммит рабочего `just-tts`.
- Дать старому процессу закончить текущее задание и отправить накопленные WAV,
  затем остановить его. Переключать с пустым spool; не переносить вслепую
  manifests с путями старого checkout. При аварийном останове дождаться возврата
  задания в очередь по истечении lease.
- Запустить новый процесс с тем же профилем, моделью и голосом; проверить его
  видимость в админке и публикацию тестового рассказа.
- Удалить Python-код, зависимости и тесты из `otgolosok/workers/tts`.
  Оставить короткий README с указанием отдельного репозитория; обновить основной
  README и активные команды запуска. Исторические планы сохраняют старые пути.
- Серверные интеграционные тесты остаются в `otgolosok` и запускаются независимо
  от наличия `../just-tts`. Ссылка на локальный соседний репозиторий сопровождается
  пояснением; постоянный URL добавить после создания remote.
- Создать отдельный коммит переноса в `otgolosok`. Push не выполнять.

## Проверки и критерии готовности

Исходные проверки в `otgolosok`:

```text
python -m unittest discover -s workers/tts -p "test_*.py"
node --test backend/external-audio.test.mjs backend/server.test.mjs backend/content-pipeline.test.mjs
```

После переноса Python-тесты выполняются из `just-tts` через
`python -m unittest discover -s tests`; серверные — прежней командой в `otgolosok`.
CI нового репозитория ограничивается установкой лёгких тестовых зависимостей и
этими тестами. Проверку с настоящими весами выполнять отдельно, с явным результатом.

Готово, когда чистая установка `just-tts` на CPU получает WAV из текста без сайта,
а режим worker через существующий API доводит задание до опубликованного MP3.
Перезапуск и повторная отправка не создают дубликатов и не публикуют частичный WAV.
Ни один runtime-путь не указывает на соседний checkout. В обоих репозиториях
зафиксированы только относящиеся к переносу файлы; секреты и веса не закоммичены.

Откат: остановить новый процесс, дождаться освобождения активного lease и запустить
старый воркер из checkout до переноса. Схема БД и API остаются совместимыми;
для проверки отката не требуется отменять остальные изменения сайта.
