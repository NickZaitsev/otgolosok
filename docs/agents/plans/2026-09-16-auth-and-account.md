# Аутентификация и личный кабинет

Дата: 2026-09-16. Статус: план реализации; код приложения не изменён.

## Результат и границы первой версии

Пользователь входит в аккаунт, сохраняет свои прогулки, видит заказанные истории
и избранное на другом устройстве. Публичная карта, опубликованные истории,
прослушивание и локальный конструктор остаются доступны гостю. Запуск новой
генерации и повторная попытка требуют входа и учитывают персональную квоту.

Предлагаемый способ входа — одноразовый код из email: первый успешный вход
создаёт аккаунт, последующие открывают существующий. Это рабочее допущение плана:
пользователь пока не выбирал способ входа. Пароли, социальные провайдеры,
платежи, подписки, публичные профили и совместное редактирование отложены.

В MVP входят профиль (email только для чтения и редактируемое имя), сохранённые
прогулки, список своих запросов на генерацию, избранное, выход с текущего/всех
устройств и удаление аккаунта. Синхронизация позиции плеера — следующий этап:
существующее локальное восстановление прослушивания сохраняется.

## 1. Основание и архитектура

План опирается на текущие файлы проекта, включая незакоммиченные изменения
OSM/TTS-пайплайна. При реализации согласовать изменения общих `server.mjs` и
`store.mjs` с [планом воркеров](2026-09-16-osm-worker-pipeline.md).

| Сейчас | Следствие для реализации |
| --- | --- |
| `next.config.ts`: `output: "export"`, Next.js 16.3.4 | `/login` и `/account` — статические оболочки с клиентской загрузкой данных |
| `backend/server.mjs`: Node HTTP API; nginx проксирует `/api/` | Auth API и проверка прав выполняются здесь, под тем же origin |
| `backend/store.mjs`: `node:sqlite`, WAL, общие jobs | Пользователи и сессии в той же SQLite; миграции отдельными версиями |
| `backend/admin.mjs`: общий `ADMIN_TOKEN`; UI хранит его в sessionStorage | Перевести редактора на сессию и серверную роль отдельным этапом |
| `src/features/walk-builder/model.ts`: один черновик `otgolosok:walk:v1` | Добавить серверную коллекцию прогулок и явный импорт локального черновика |
| `src/features/explore/map-jobs.ts`: задания устройства в localStorage | Серверный список запросов аккаунта, независимый от конкретного браузера |
| `src/lib/audio/playback-progress.ts`: прогресс привязан к версии аудио | Сохранять эту привязку при будущей синхронизации |
| `public/sw.js`, `src/features/generator/offline.ts`: кешируются истории и MP3 | Не допустить попадания приватных ответов в общий офлайн-кеш |

Изучены локальные руководства Next.js:
`node_modules/next/dist/docs/01-app/02-guides/static-exports.md` и
`node_modules/next/dist/docs/01-app/02-guides/authentication.md`.
В static export недоступны динамические Route Handlers, серверное чтение cookies,
Server Actions и Proxy. Поэтому не переносить auth в `src/app/api`, не добавлять
защиту через Next.js middleware/Proxy и не менять способ production-развёртывания.
Клиентское перенаправление на вход служит интерфейсу; доступ защищает API.

Перед реализацией auth провести короткую проверку поддерживаемой auth-библиотеки
с email OTP: интеграция с обычным Node HTTP, SQLite/Node 24, opaque sessions,
отзыв сессий, CSRF, миграции и обслуживание зависимости. Например, проверить
Better Auth как кандидата, не считать совместимость заранее доказанной.
Зафиксировать выбор и версию отдельным решением; при подходящем кандидате
использовать его механизмы и таблицы через адаптер. Описанные ниже сущности и
контракты — требования к поведению, а не требование дублировать таблицы библиотеки.
Если кандидат не подходит, сначала пересмотреть выбор, не заменять его поспешно
самописной криптографией. Этот выбор блокирует реализацию хранилища auth,
но не разработку кабинета по контрактам API.

## 2. Сценарии входа и сессии

1. `/login` принимает email и безопасный относительный `returnTo` из разрешённых
   маршрутов. Запрещены внешние URL, `//`, неоднозначное кодирование и переходы
   на произвольные адреса. После входа возвращать пользователя к его действию,
   но не запускать платную генерацию автоматически.
2. Запрос кода создаёт challenge и отправляет письмо. Ответ одинаков для нового
   и существующего email. Отдельная ошибка доступности почты не раскрывает
   существование аккаунта; коды и адреса не попадают в пользовательские ошибки.
3. Код действует 10 минут, одноразовый, максимум 5 попыток на challenge.
   Повторная отправка не чаще раза в минуту; новый код аннулирует предыдущий.
   Начальные лимиты: 5 отправок на email в час, 20 на IP в час, плюс глобальный
   предел расходов на почту. Значения конфигурируемы; подбор ограничен и по IP.
4. Проверка кода и его погашение атомарны. Успех подтверждает email, создаёт
   пользователя при необходимости и новую случайную сессию. Гонки двух запросов
   не создают двух пользователей и не позволяют дважды использовать код.
5. Сессия имеет абсолютный срок 30 дней и срок бездействия 7 дней; сроки проверяет
   сервер. Ограничить частоту записи `last_seen_at`, чтобы не блокировать SQLite.
   Вход и повышение привилегий заменяют идентификатор сессии.

Email валидируется и нормализуется по единой задокументированной политике:
trim, регистр по принятому правилу, без удаления точек и `+suffix`. В БД уникален
нормализованный email. Имя ограничено по длине и выводится как текст.

Cookie production: `__Host-otgolosok-session`, `HttpOnly`, `Secure`, `SameSite=Lax`,
`Path=/`, без `Domain`. В локальном HTTP — отдельное имя без `__Host-`, только
при явно заданном development-режиме. Production с небезопасной конфигурацией
не запускается. В БД хранить хеш случайного токена сессии, в браузере — только
cookie; не сохранять bearer/JWT в localStorage или sessionStorage.

Низкоэнтропийный OTP хранить в защищённой форме средствами выбранной библиотеки;
простой SHA-256 короткого кода недостаточен. При собственной серверной обвязке
использовать HMAC с отдельным секретом и привязкой к challenge, без записи кода
в логи. Почтовый адаптер внедряется зависимостью; тесты используют поддельную
доставку, локальная разработка — локальный почтовый приёмник.

## 3. Авторизация и границы данных

Ввести общие `requireSession`, `requireRole` и проверки владельца на уровне
операций хранилища. `userId` берётся из сессии, входной `ownerId` отвергается.
Запросы к прогулкам фильтруются одновременно по ID и владельцу. Чужой объект
отвечает `404`, отсутствие сессии — `401`, недостаточная роль — `403`.

| Действие | Гость | Пользователь | Редактор |
| --- | --- | --- | --- |
| Публичная карта, готовые истории, MP3 и встроенные прогулки | Да | Да | Да |
| Локальный конструктор и публичный расчёт маршрута | Да, с лимитами | Да, с лимитами | Да, с лимитами |
| Новая генерация/исследование и retry | Нет | По квоте и правам | По редакторским правилам |
| Профиль, избранное, сохранённые прогулки, история запросов | Нет | Только свои | Только свои |
| Редактирование общего каталога и публикация | Нет | Нет | Да |

Адресные jobs сейчас дедуплицируются глобально по адресу. Не добавлять им
единственного владельца: один job может обслужить нескольких пользователей.
Ввести `user_generation_requests` — связь аккаунта с общим заданием. Она хранит
время запроса, тип операции и ключ идемпотентности; уникальность как минимум
`(user_id, idempotency_key)`. Привязка к job, проверка квоты и создание запроса
выполняются одной транзакцией. Повторная доставка запроса не расходует квоту.
Повторное использование готового публичного результата не считается генерацией;
новая работа/retry расходуют персональный и существующий глобальный лимит.

Разделить публичное содержимое истории и приватные сведения о заказе. На
публичном `/api/story-jobs/:id` возвращать только разрешённую проекцию, без
владельцев, email, служебных checkpoints и истории запросов. Retry требует связи
с аккаунтом или роли редактора и сохраняет текущую проверку revision.
Для незавершённых jobs определить минимальный публичный статус, остальное
читать через личный API. Знание UUID не даёт права изменять задание.

Исследования прогулок содержат стартовую точку пользователя: новые
`walk_research` принадлежат аккаунту, а их дедупликация учитывает владельца.
Закрыть прямой GET по UUID, lookup и retry для чужих аккаунтов. Для старых
исследований разрешить привязку только по проверенному `recoveryToken`,
атомарно и один раз; без доказательства владения не импортировать.
Проверить создаваемые исследованием дочерние истории и их проекции.

Публичные истории и аудио остаются общими. Личными являются подборки, выбранные
точки и связь пользователя с контентом. GPS-трек и текущую геопозицию в профиль
не отправлять; выбранная стартовая точка хранится только при явном сохранении
прогулки/запуске исследования. В UI заранее объяснить это поведение.

Worker credentials из OSM/TTS-пайплайна остаются отдельным типом доступа:
пользовательская cookie не даёт прав воркера, токен воркера — прав кабинета.

## 4. Хранилище и миграции

| Сущность | Основные поля и ограничения |
| --- | --- |
| `users` | UUID, уникальный нормализованный email, подтверждение email, имя, роль `user/editor`, timestamps |
| `sessions` | Хеш токена, user FK, absolute/idle expiry, last seen; возможность отзыва |
| `login_challenges` | Challenge ID, нормализованный email, защищённый код, expiry, attempts, consumed_at |
| `auth_rate_limits` | Ограниченные по времени счётчики отправок/проверок; очистка истёкших записей |
| `user_walks` | UUID, user FK, title, versioned validated snapshot, revision, timestamps |
| `user_favorites` | user FK, тип/ID публичного объекта; составной уникальный ключ |
| `user_generation_requests` | user FK, job FK, тип операции, idempotency key, timestamps |
| `account_imports` | user FK, import ID и результат; защита повторного импорта |

Добавить явный реестр schema migrations. Применять версии транзакционно до
приёма запросов; не переписывать старые JSON jobs массово без необходимости.
Индексы: email, session hash, expiry, `(user_id, updated_at, id)`, связи с jobs.
Включить и проверить foreign keys для новых отношений. Новые модули хранилища
получают существующее соединение SQLite и транзакционный helper.

Snapshot прогулки проходит серверную проверку схемы, координат, количества
остановок, ссылок на истории и размера тела. Не доверять рассчитанным клиентом
полям стоимости или правам. Сохранение списка прогулок не запускает генерацию.
Для обновления обязательна revision: конфликт даёт `409` и возможность сохранить
копию. Ограничить размер коллекций, добавить cursor pagination со стабильной
сортировкой; не отдавать всю историю без предела.

## 5. Контракты API

Ниже внешний контракт приложения; конкретные auth-маршруты можно адаптировать
к выбранной библиотеке через единый клиентский модуль.

| Метод и путь | Поведение |
| --- | --- |
| `POST /api/auth/email/start` | Email → нейтральный ответ и challenge ID, ограничения отправок |
| `POST /api/auth/email/verify` | Challenge + код → сессия и безопасная проекция пользователя |
| `GET /api/auth/session` | Пользователь и CSRF token либо гостевое состояние; `no-store` |
| `POST /api/auth/logout` | Отзыв текущей сессии и очистка cookie; идемпотентно |
| `POST /api/auth/logout-all` | Отзыв всех сессий пользователя, включая текущую |
| `GET/PATCH /api/me` | Профиль; PATCH разрешает только имя |
| `GET/POST /api/me/walks` | Список с pagination / создание с idempotency key |
| `GET/PATCH/DELETE /api/me/walks/:id` | Чтение, изменение/удаление с проверкой владельца и revision |
| `GET /api/me/requests` | История собственных запросов, статусы и ссылки на результаты |
| `GET /api/me/favorites` | Избранное с pagination |
| `PUT/DELETE /api/me/favorites/:type/:id` | Идемпотентное добавление/удаление разрешённого публичного объекта |
| `POST /api/me/import` | Проверенный пакет локальных данных, import ID, результат по каждому элементу |
| `DELETE /api/me` | Удаление аккаунта после свежего подтверждения email |

Все изменяющие запросы из браузера, включая login/logout, требуют точного
`Origin`, проверки Fetch Metadata и ожидаемого `Content-Type`. После входа
дополнительно использовать CSRF token, связанный с сессией. Для login-flow
сохранить защиту выбранной библиотеки от login CSRF. Не включать произвольный
credentialed CORS. Ограничить размер тела и набор полей каждого endpoint.

Лимиты привязывать к достоверному IP: доверять forwarded headers только от
настроенного nginx/ingress, который перезаписывает входное значение. Не делать
один общий счётчик на IP внутреннего nginx. Счётчики переживают рестарт backend.
Истёкшие challenge/сессии и счётчики очищаются ограниченными пакетами.

## 6. Интерфейс и перенос локальных данных

Добавить `src/app/login/page.tsx`, `src/app/account/page.tsx`, компоненты в
`src/features/auth/` и `src/features/account/`, общий API-клиент и SessionProvider.
Статические страницы не содержат данных пользователей. Кнопка «Личный кабинет»
доступна из основного интерфейса, конструктора и генератора.

Состояния сессии: загрузка, гость, пользователь, сеть недоступна. Ошибку сети
не трактовать как подтверждённый выход. На `401` сбрасывать приватное состояние
и предлагать повторный вход, сохраняя безопасный локальный черновик.
У форм есть labels, автозаполнение email/одноразового кода, управление фокусом,
доступные сообщения ошибок, блокировка повторной отправки и таймер resend.

В кабинете предусмотреть пустые списки, загрузку, частичную ошибку, исчерпанную
квоту, конфликт сохранения и удалённый публичный объект. Раздел «Мои прогулки»
открывает запись через `/walk?id=…`; неизвестные IDs не требуют динамических
Next.js страниц. Конструктор поддерживает сохранение новой прогулки и обновление
существующей, сохраняя локальный режим гостя.

После первого входа предложить явно перенести локальный черновик и выбранные
публичные истории. Показать состав переноса; не загружать всё из браузера молча.
Перед отправкой и на сервере валидировать данные, присвоить стабильный import ID.
Локальную копию удалять только после подтверждённого результата и выбора
пользователя. Повтор после обрыва сети возвращает тот же результат.

ID из старого списка map jobs не доказывает авторство: такие истории можно
добавить в избранное, но нельзя приписывать аккаунту чужую генерацию или право
retry. Локальный черновик импортируется как копия; исследование привязывается
только по recovery token. Повреждённые элементы возвращаются отдельными ошибками.

Локальные данные аккаунта именовать с `userId`, гостевые — отдельно. На выходе
остановить запросы и autosave, очистить память и приватные локальные данные,
уведомить другие вкладки через BroadcastChannel либо storage event. Поздний
ответ старой сессии не должен восстановить предыдущий профиль. При смене
аккаунта никогда не переносить данные прежнего владельца автоматически.

## 7. Офлайн, редактор и эксплуатация

Для `/api/auth/*`, `/api/me/*`, приватных исследований и редакторского API
установить `Cache-Control: no-store` и явный обход service worker. Проверка
наличия Authorization в нынешнем SW недостаточна для cookie-сессии.
Обновить `public/sw.js`, генератор SW и существующие тесты кеша. Публичные MP3
и безопасные проекции опубликованных историй можно сохранять как сейчас.
При обновлении удалить старые кеши, которые могли содержать приватные поля;
новый кеш никогда не заполнять полным ответом личного API.

В MVP кабинет требует сети: не кешировать профиль и серверные приватные списки.
Локальный гостевой конструктор и уже загруженные публичные записи работают
офлайн. При выходе без сети очистить локальный интерфейс, заблокировать его
автовосстановление и поставить отзыв сессии на повтор при восстановлении связи;
явно сообщить, что серверный выход ещё не подтверждён. HttpOnly cookie клиент
самостоятельно удалить не может. Проверить этот сценарий во всех вкладках.

После готовности пользовательского входа перевести `/admin` на роль `editor`:
убрать поле общего токена и sessionStorage, заменить `credentials: "omit"`
на same-origin и подключить CSRF. Первого редактора назначать отдельной
серверной CLI-командой по подтверждённому user ID/email; публичного endpoint
назначения ролей нет. Роль проверяется по актуальной БД, её отзыв действует
сразу. Перед отключением `ADMIN_TOKEN` проверить вход назначенного редактора.
Если требуется переходный период, ограничить старый механизм отдельным флагом
и датой удаления; он не создаёт пользовательские сессии.

Удаление аккаунта требует кода подтверждения с отдельным purpose, действующего
не более 10 минут. Атомарно отозвать сессии и удалить профиль, прогулки, избранное
и связи запросов; общие опубликованные истории/MP3 сохраняются. Приватные
исследования отменить и очистить с учётом активного worker: он не должен вновь
записать удалённые личные данные. Удаление проверить отдельно от публикации.
Описать срок хранения резервных копий и процедуру повторного удаления после
восстановления snapshot; удаление из live-БД не обещает немедленного стирания backup.

Добавить backend-only настройки почты, секрета OTP/auth, лимитов и cookie-режима
в `.env.example` и `compose.yaml`; значения секретов не попадут в Next.js build.
Без почтовой конфигурации публичный сайт работает, вход возвращает понятную
недоступность. Настроить timeout/retry отправки и SPF/DKIM/DMARC домена отправителя.
Не отправлять email, коды, cookies, CSRF и recovery tokens в Airouter или access logs.
Метрики содержат счётчики доставки, входов, отказов, `429` и ошибок миграции.

Локальную проверку проводить под одним origin через nginx или backend со
`STATIC_DIR=out`. `pnpm dev` сам по себе не обслуживает этот API: для разработки
с HMR нужен локальный reverse proxy, который направляет страницы на Next dev,
а `/api/` на backend. Не обходить это отключением Secure/CSRF в production.

## 8. Порядок реализации и проверки

Каждый этап — отдельный проверяемый коммит; auth и обязательный вход для
генерации включаются только после готовности связанных клиентских сценариев.

1. **Зафиксировать контракты и зависимость.** Проверить auth-библиотеку, выбрать
   почтовый адаптер, утвердить политику публичных данных и квот. Сделать минимальную
   интеграционную проверку: реальный HTTP → Set-Cookie → защищённый API → logout.
2. **Миграции и серверный auth.** Добавить auth-модули, адаптер почты и тесты с
   управляемым временем. Проверить миграцию существующей БД, повторный запуск,
   неверный/просроченный/повторный код, гонку verify, лимиты, expiry и отзыв сессий.
3. **Авторизация данных.** Добавить владельцев прогулок/исследований и связи
   общих jobs, квоты, idempotency. Проверить двух пользователей: чужие IDs,
   обход через старый endpoint, lookup, retry, подмену userId и запросы редактора.
   Проверить независимость worker-token и пользовательской сессии.
4. **Вход и кабинет.** Добавить страницы, навигацию, профиль, списки, избранное
   и серверное сохранение прогулок. Проверить пустые состояния, ошибки сети,
   `401`, pagination, конфликты revision и возвращение к исходному действию.
5. **Импорт и офлайн.** Добавить явный перенос, изоляцию локальных данных,
   обновление SW и выход во всех вкладках. Проверить прерванный импорт, повтор,
   смену аккаунта, запоздалый ответ, офлайн-выход и продолжение публичного аудио.
6. **Редактор, удаление, выпуск.** Назначить первого редактора, переключить admin,
   проверить удаление при активном job. Подготовить инструкции, backup и rollout.

Серверные тесты разместить рядом с модулями (`backend/auth*.test.mjs`,
`backend/account*.test.mjs`), клиентские модели — в Vitest. Для cookie, CSRF,
nginx и SW добавить небольшой браузерный smoke-набор, например на Playwright,
с тестовым почтовым адаптером; текущий проект такого набора ещё не имеет.
Обязательные сценарии: первый вход, второй браузер видит сохранённую прогулку,
другой аккаунт её не видит, выход отзывает cookie, чужой Origin блокируется,
редакторские действия недоступны пользователю, приватный API не читается из кеша.

Перед выпуском выполнить `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`,
`docker compose config --quiet` и браузерный smoke через production nginx по HTTPS.
Проверить direct navigation на `/login`, `/account`, `/walk?id=…`, передачу
Cookie/Set-Cookie и сохранение HttpOnly/Secure/SameSite. Сборка должна остаться
статическим export и не требовать секретов почты.

Сначала снять согласованный snapshot SQLite и проверить восстановление.
Выкатывать добавочные миграции и backend, затем клиент/SW, затем включать
auth-required для генерации; старым вкладкам возвращать понятный `401`.
Откат интерфейса не должен открывать приватные endpoints или возвращать публичный
доступ к исследованиям. При сбое временно отключать вход/новую генерацию,
сохраняя публичное прослушивание; не откатывать безопасность вместе с UI.

## Критерии готовности

- Первый вход создаёт один подтверждённый аккаунт, повторный открывает его;
  истёкший/использованный код и отозванная сессия не работают.
- Сохранённая прогулка, избранное и собственные запросы видны на другом устройстве;
  доступ к чужим данным закрыт на всех новых и старых маршрутах API.
- Гостевое прослушивание и локальные черновики сохраняются; перенос данных явный
  и повторяемый без дублей. Квоты нельзя обойти сменой вкладки или повтором запроса.
- Выход, смена аккаунта и удаление не оставляют приватные данные в общих кешах;
  пользователь понимает ограничения выхода без сети.
- `/admin` использует подтверждённую серверную роль, worker API сохраняет
  независимую авторизацию, удаление аккаунта не разрушает общий каталог.
- Проверки пройдены, доставка почты проверена, backup восстановлен, инструкция
  развёртывания и ограничения первой версии записаны в документации.
