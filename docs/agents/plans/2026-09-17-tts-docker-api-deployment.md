# План: TTS в Docker на Linux, API и подключение Otgolosok

Status: plan, 2026-09-17.

> Снимок на дату создания: сведения о коде могут устареть. Перед реализацией проверить пути, функции и контракты по актуальным исходникам. Документ написан по-русски согласно AGENTS.md; структура и строка Status следуют make-plan.

## Контекст

Развернуть `C:\00_projects\just-tts` и модифицированные исходники из
`C:\F5-TTS Portable\F5-TTS` на Linux с NVIDIA GPU. Предоставить самостоятельный
HTTP API и подключить к нему backend Otgolosok в рамках этой же задачи.
Указанный пользователем путь `C:\00\_projects\just-tts` отсутствует;
проверенный локальный путь приведён выше.

Базовый образ: `nvidia/cuda:12.0.1-cudnn8-runtime-ubuntu22.04`.
Драйвер сервера менять нельзя; его версия, GPU и объём VRAM пока неизвестны.
Пользователь предполагает, что CUDA 12.0 может быть максимумом для драйвера.
Это предположение нужно проверить, а не превращать в обещание совместимости.

Результат для пользователя сайта: существующее задание на локальную озвучку
получает MP3 от удалённого TTS-сервиса и публикуется обычным способом.
Постоянное хранение аудио остаётся на сервере сайта. GPU-сервер хранит только
ограниченный временный набор результатов и ресурсы моделей.

Внешние ресурсы при подготовке: индекс PyTorch
`https://download.pytorch.org/whl/`, checkpoint
`https://huggingface.co/Misha24-10/F5-TTS_RUSSIAN`, вокодер
`https://huggingface.co/charactr/vocos-mel-24khz`, ресурсы Silero и подготовки
текста. Предпочесть уже проверенные локальные веса с SHA-256. Платный API
синтеза не требуется; вычисления, хранение и трафик оплачиваются по условиям
сервера. Проверить условия использования выбранных весов перед публикацией.

## Согласованные решения

1. Linux, Docker, сохранение указанного базового образа и существующего драйвера.
2. Изменения сайта входят в этот план, а не выносятся в отдельную задачу.
3. Первая версия F5 использует существующий CLI и параметры локальной сборки;
   модель загружается для каждого задания.
4. Сервер воркера не должен накапливать аудио. Финальное хранение — на сайте.
5. По предложению пользователя переносим WAV → MP3 на воркер; последующие
   сообщения «Go on» разрешают продолжить подготовку плана.

Рабочие настройки реализации ниже — рекомендации, а не отдельно полученные
ответы пользователя: оба движка, один исполнитель, очередь SQLite, выбор
движка сайта через существующий `LOCAL_TTS_ENGINE`, без нового UI. Backend
сайта отправляет задания, скачивает MP3 и подтверждает сохранение. Расположение
серверов неизвестно, поэтому инструкция включает закрытую Docker-сеть и HTTPS
между разными серверами. Конкретные DNS/порты/секреты задаются при развёртывании.

- `backend/server.mjs:96`: `/api/worker/v1/claim` и `/jobs/{id}/...` —
  существующий pull-протокол. Обработчик результата проверяет SHA-256,

- `backend/audio-ingest.mjs:13`, `ingestAudio()`, принимает и WAV, и MPEG,
  но всегда выполняет FFmpeg loudnorm и кодирование MP3: повторное кодирование

- Текущий выход: loudnorm `I=-16:TP=-1.5:LRA=11`, mono, 24 kHz, 64 kbit/s,
  удаление метаданных. Лимит загрузки 64 MiB, длительности до 600 секунд;
  минимум длительности F5 отдельно регулируется профилем публикации сайта.

## Реализация

### 0. Проверить GPU и выбрать зависимости до фиксации Docker-сборки

В `just-tts/docs/deployment-linux.md` записать команды диагностики, ожидаемые
результаты и затем фактически проверенную матрицу версий:

- `nvidia-smi`: версия драйвера, GPU, VRAM; `uname -m`; Docker/Compose и доступ
  GPU из `docker run --rm --gpus all nvidia/cuda:12.0.1-cudnn8-runtime-ubuntu22.04 nvidia-smi`.
- Если NVIDIA Container Toolkit отсутствует, настроить Docker runtime по
  инструкции NVIDIA, сохранив драйвер; перезапуск общего Docker согласовать
  при развёртывании, поскольку он затрагивает другие контейнеры.
- Различать toolkit хоста, CUDA в образе и библиотеки из wheel PyTorch.
  Надпись CUDA Version в nvidia-smi не означает установленный toolkit.
- Python 3.12 + torch/torchaudio 2.5.1 cu121 — только кандидат для проверки,
  если разрешены такие библиотеки внутри указанного образа. Проверить поддержку
  архитектуры GPU, ограничения minor compatibility/PTX и реальный синтез.
- Если разрешена строго CUDA 12.0 внутри контейнера, не устанавливать cu121
  молча. Зафиксировать невозможность выбранной сборки и отдельно согласовать
  вариант совместимого стека/сборки; не менять драйвер, образ или устройство
  на CPU автоматически.
- После чистой Linux-установки, `pip check` и реального синтеза закрепить
  torch, torchaudio, torchcodec (если требуется), numpy, transformers,
  x-transformers, vocos и транзитивные зависимости в
  `just-tts/deploy/constraints-linux.txt`. Не использовать Windows freeze.

Ссылки для повторной проверки:
`https://docs.nvidia.com/deploy/cuda-compatibility/minor-version-compatibility.html`,
`https://pytorch.org/get-started/previous-versions/`.
Без доступа к серверу этот этап остаётся непроверенным; остальной код можно
реализовывать и тестировать с локальными fixtures, но GPU-деплой не объявлять готовым.

### 1. Подготовить переносимую поставку моделей и F5

Создать `just-tts/deploy/prepare-f5.py`, `deploy/f5-source-manifest.json`,
`examples/f5-linux.toml`, `.dockerignore`. Скрипт формирует отдельный build
context из allowlist локальных исходников F5, фиксирует хеши и изменения,
сохраняет лицензии. Не копирует venv, Windows Python/FFmpeg/Git, `.env`,
историю Git, outputs и кэши. Манифест позволяет проверить точную поставку
модификаций; сервер получает подготовленный архив исходников, а не зависимость
от соседнего Windows-каталога. Скрипт отказывает при недостающих ресурсах.

Веса, vocab, yaml и референс передавать отдельно с контрольными суммами;
монтировать как read-only. Предзагрузить вокодер и ресурсы нормализатора,
акцентора в контролируемый кэш, проверить запуск без новых скачиваний.
Нормализатор может требовать отдельные ресурсы вне HF_HOME — учесть все пути.

Изменить `just_tts/f5.py`: переносимый Python, управляемый HF_HOME,
временные файлы в каталоге задания на одном filesystem, атомарный финальный
rename. Прежде исправления EXDEV добавить воспроизводящий тест в `tests/test_f5.py`.
Параметры голоса и CLI сохраняются; Linux-профиль задаёт CUDA явно.

### 2. Создать контракт MP3 и ограниченный жизненный цикл файлов

Создать `just_tts/audio.py`, `just_tts/storage.py`, их тесты.
Интерфейс `encode_mp3(wav_path, output_path, *, timeout_seconds) -> AudioArtifact`.
Версия профиля кодирования: `mp3-mono24k-64k-loudnorm-v1`; параметры совпадают
с текущим backend. WAV → loudnorm → MP3 выполняется один раз на воркере.
Проверить результат ffprobe и полным декодированием с таймаутом, вычислить
SHA-256, записать размер, длительность и версию кодирования.

Порядок: создать MP3 `.pending` → проверить → атомарно переименовать →
зафиксировать готовность в БД → удалить WAV и промежуточные chunks.
После сбоя согласовать БД и filesystem: `.pending` никогда не выдаётся,
неподтверждённые файлы готовыми не считаются. Повторная передача использует
тот же MP3 и hash, не повторный недетерминированный синтез F5.

Предлагаемые конфигурируемые defaults в `.env.example` и `config.py`:

| Настройка | Значение | Назначение |
|---|---:|---|
| `TTS_MAX_QUEUED_JOBS` | 100 | Ограничение принятых ожидающих заданий |
| `TTS_MAX_TEXT_CHARS` | 20000 | Ограничение входного текста |
| `TTS_MAX_AUDIO_SECONDS` | 600 | Ограничение результата |
| `TTS_RESULT_TTL_SECONDS` | 86400 | Удаление невостребованного MP3 через сутки |
| `TTS_SPOOL_MAX_BYTES` | 2147483648 | Бюджет временных файлов, БД и результатов |
| `TTS_MIN_FREE_BYTES` | 1073741824 | Резерв свободного места |
| `TTS_JOB_TIMEOUT_SECONDS` | 1800 | Предел выполнения одного задания |

Один исполнитель. Проверять место перед принятием/запуском, резервировать
бюджет временного WAV, следить за ростом файлов во время subprocess и завершать
его при превышении. Не считать предварительный statfs гарантией; обработать
ENOSPC. На отдельном volume предусмотреть filesystem quota для жёсткой границы.
Кэш моделей учитывается отдельно: предзагрузка, отсутствие безграничного
скачивания ревизий во время работы. Docker stdout-логи тоже ротируются.

Успешное подтверждение удаляет MP3 сразу; отсутствие подтверждения — по TTL,
с состоянием `expired`, а не ложным успехом доставки. История, idempotency keys
и tombstones живут ограниченное время (7 суток), очистка каждые 5 минут и при
старте; не удалять файл активного скачивания. Ограничить SQLite WAL и выполнять
checkpoint/обслуживание, чтобы лимит охватывал и метаданные.

### 3. Добавить самостоятельный HTTP API в just-tts

Создать `just_tts/api.py`, `jobs.py`, `executor.py`, `docs/http-api-v1.md`.
В `pyproject.toml` добавить extra `api` с совместимыми фиксируемыми
FastAPI/Uvicorn. В `__main__.py` добавить `serve`; существующие CLI-команды
и режим исходящего worker сохранить. Один API-процесс и один управляемый
исполнитель, без нескольких Uvicorn workers и копий модели.

SQLite хранит задания до ответа 202; состояния:
`queued`, `running`, `succeeded`, `failed`, `expired`, `acknowledged`.
Синтез обоих движков использует текущую подготовку текста. F5 вызывается
через CLI без shell; HTTP-обработчик не блокируется на синтезе.

Контракт, все рабочие методы требуют `Authorization: Bearer`:

- `GET /v1/profiles`: движки, голоса, model/config/reference hashes,
  preparationVersion, encodingVersion; без локальных путей.
- `POST /v1/jobs`: `requestId`, `profileId`, `text`, ожидаемые версии/хеши;
  202 `{id,status}`. Уникальный requestId и hash входа: повтор возвращает то же
  задание, другой вход под тем же ключом — 409. Профили только из allowlist.
- `GET /v1/jobs/{id}`: состояние, ограниченный безопасный код ошибки;
  при готовности размер, SHA-256 MP3, длительность и фактические метаданные TTS.
- `GET /v1/jobs/{id}/audio`: поток `audio/mpeg`, Content-Length, SHA-256;
  409 если ещё не готово, 410 если удалено по TTL.
- `POST /v1/jobs/{id}/ack`: ожидаемый SHA-256; после сохранения на сайте.
  Повторное подтверждение идемпотентно. Удаление и запись receipt восстанавливаются
  после сбоя; 204 возвращать после завершения очистки. Сохранить tombstone.
- `GET /healthz`, `GET /readyz`: минимальный статус; readiness проверяет
  конфигурацию, ресурсы и работоспособность исполнителя без генерации на каждый probe.

Токен задаётся через `TTS_API_TOKEN`, не попадает в URL/логи/браузер. Версия v1
использует один доверенный серверный клиент/токен, без multi-tenant обещаний.
Не принимать от клиента команды, пути, URL референсов или callback URL.
Ограничить JSON по байтам, длительность скачивания и число соединений.
Переполнение очереди — 429 с Retry-After, нехватка диска — 503.
На shutdown остановить приём, завершить/прервать subprocess и сохранить
состояние; после рестарта незавершённый синтез пометить `failed/INTERRUPTED`.
Ожидающие задания и проверенные результаты переживают рестарт.

### 4. Подключить backend сайта и сохранить гарантии существующей очереди

Создать `backend/tts-api-client.mjs`, `backend/tts-api-worker.mjs` и тесты.
Интерфейсы: `createTtsApiClient({baseUrl,token,fetchImpl,...})` и
`startTtsApiWorker({store,client,audioDirectory,signal,...})` с `stop()`.
Запуск/остановку подключить в `backend/server.mjs` аналогично существующим
worker/contentWorker. UI и маршруты создания локальной озвучки сохраняются.

Настройки в `.env.example`, `compose.yaml`, `backend/local-tts.mjs`:
`LOCAL_TTS_TRANSPORT=worker|http` (default `worker` для совместимости),
`TTS_API_URL`, `TTS_API_TOKEN`, таймауты запросов и poll interval.
`LOCAL_TTS_ENGINE` продолжает выбирать silero/f5. HTTP-режим требует полного
конфига, иначе ошибка запуска. Не включать оба транспорта на одни и те же
профили: внешний claim для выбранных HTTP-профилей не выдаёт задания старому
воркеру. Подключать через явную фильтрацию, покрытую тестом.

В `backend/store.mjs` добавить устойчивое соответствие локального задания,
поколения попытки, requestId, remoteJobId и квитанции; миграция аддитивная.
Backend берёт существующий lease, поддерживает heartbeat во время ожидания,
скачивания и приёмки, сверяет профиль через `/v1/profiles`, отправляет задание.
Новый requestId генерируется/сохраняется ДО POST; потерянный ответ повторяется
с прежним requestId. После перезапуска продолжить уже созданное удалённое
задание; при новом lease явно сверить актуальность исходного текста/профиля.
Только терминальная неуспешная попытка создаёт новую generation/requestId.

Публикация: скачать MP3 во временный файл → проверить hash, профиль и формат →
атомарно сохранить файл на сайте → `acceptExternalAudio()` → записать durable
receipt и pending ack → подтвердить удаление удалённого файла. Receipt и
pending ack создавать в одной транзакции с приёмкой, чтобы сбой после commit
не терял очистку. После durable ack пометить доставку законченной.
При утере lease или изменении текста результат не публиковать; удалить
неиспользуемый локальный временный файл, удалённый результат доживёт до TTL.

Создать общий `backend/tts-result.mjs`, если нужен перенос проверок метаданных
из существующего worker result endpoint: оба транспорта должны проверять
подготовку текста, model/config/reference hashes и голос одинаково.
Не обходить в новом транспорте проверку ревизии, lease, минимум длительности
F5 и защиту опубликованного аудио при неудачной повторной озвучке.

В `backend/audio-ingest.mjs` добавить явный режим приёма готового MP3
`ingestPreparedMp3(...)`, выбираемый доверенным серверным кодом нового
транспорта. Существующий WAV endpoint сохраняет кодирование по старому контракту.
Для prepared MP3: hash/лимит/codec/channels/sample rate/duration, полное
декодирование FFmpeg с таймаутом, при необходимости измерение loudness без
перекодирования; проверка encodingVersion обязательна. Некорректный файл
отклоняется, автоматической повторной MP3-компрессии нет. Не доверять одному
Content-Type. Финальные bytes/hash на сайте совпадают с проверенным MP3 воркера.

Повторы: сеть, 429 и временные 5xx — ограниченный exponential backoff с jitter
и Retry-After; POST только с requestId. 401/403, несовместимый профиль и
неверные данные не повторять бесконечно. Poll ожидающего задания — нормальное
ожидание, не ошибка. Лимиты транспортных повторов и бизнес-попыток разделить;
существующий `failExternalAudio()` повторяет ошибки до max_attempts, поэтому
добавить явную терминальность для детерминированных ошибок с сохранением
совместимости старых вызовов. Ack повторяется из outbox; 410 означает истечение
TTL и завершает очистку без потери уже опубликованного аудио.

### 5. Docker, эксплуатация и переключение

Создать в just-tts `Dockerfile`, `compose.yaml`, `deploy/compose.same-host.yaml`,
дополнить `README.md` и `docs/deployment-linux.md`.
Использовать указанный CUDA runtime, Python 3.12, FFmpeg/ffprobe, libsndfile,
проверенные зависимости. Runtime-образ не содержит CUDA compiler; если пакет
требует сборки расширений, решить это в проверенной стадии сборки, не менять
незаметно базовую CUDA. Не переносить из примерного Dockerfile Playwright,
ботов и другие зависимости, которых нет в TTS-задаче. Не маскировать ошибки
сборки конструкцией `|| true` вокруг установки.

Непривилегированный пользователь, GPU reservation выбранного устройства,
read-only модели, writable data/cache с заданными правами, restart policy,
healthcheck, ограниченные логи, stop grace period. Не использовать privileged.
Описать хранение SQLite на локальном volume и лимиты памяти/CPU по измерениям.

Для одного хоста — общая закрытая Docker-сеть, без публичного порта TTS.
Для разных — HTTPS reverse proxy, серверный токен, доступ backend;
браузер обращается только к Otgolosok. Сертификат и DNS зависят от окружения,
не вшивать неподтверждённый адрес. Токены не включать в image/build context.

Порядок развёртывания: подготовить исходники и веса с manifest → проверить
GPU-стек → собрать образ → прогреть/проверить оба профиля → проверить API вручную →
дождаться окончания старых lease → переключить сайт на HTTP → выполнить
реальную озвучку → убедиться, что MP3 опубликован и spool очищен.
Фактические команды build/up/curl, подготовку токена и volumes привести в README.

Откат: остановить HTTP dispatcher, дать завершиться или истечь lease,
вернуть `LOCAL_TTS_TRANSPORT=worker` и совместимые старые профили, запустить
прежний исходящий воркер. Сохранить уже опубликованные MP3, SQLite и receipts;
не запускать конкурирующие транспорты на одном профиле. Закрепить версии image
и исходников для возврата, не полагаться на latest.

## Тестирование и проверка

Во время реализации проверять поведение, не ограничиваться вызовами mocks:

1. Python: параметры CLI и Linux-пути, EXDEV, конвертация настоящего короткого
   WAV, проверка MP3, удаление WAV, сбой FFmpeg, таймаут, ENOSPC, превышение
   лимита временных файлов, безопасная очистка только каталога задания.
2. API/SQLite: одинаковый requestId, конфликт входа, restart после POST/rename,
   один исполнитель, interrupted job, очередь и диск заполнены, TTL, повторный
   ack, сбой удаления, активное скачивание во время очистки, ограничения БД/WAL.
3. Backend: потерянный ответ POST, рестарт после отправки и после приёмки,
   outbox ack, истечение lease/TTL, смена текста, профиль CPU/GPU с другим hash,
   отказ авторизации, детерминированная ошибка без бесконечных повторов.
4. Приём MP3: битый/обрезанный файл, неверный hash/codec/длительность,
   несовместимый encodingVersion; bytes сохраняются без перекодирования.
   Старый WAV и существующая worker API остаются совместимыми.
5. Сквозной локальный тест: очередь сайта → API с тестовым синтезом → MP3 →
   публикация → ack → пустой spool. Отключить сайт, наполнить spool до границы,
   проверить ограничение и восстановление, отсутствие дубликатов публикации.
6. На Linux GPU: короткий и длинный русский текст, оба движка, цифры/ударения,
   прослушивание MP3, peak VRAM/время/диск, реальная публикация и очистка после
   перезапуска. Никаких платных API в автоматических тестах.

Команды реализации: в just-tts `uv run ruff check .`, `uv run pyright`,
`python -m unittest discover -s tests -v` в установленном окружении;
в Otgolosok `npm run lint`, `npm run typecheck`, `npm test`.
Также `docker compose config`, чистая Docker-сборка, `pip check` и GPU smoke.
Если реализация затрагивает Next.js, сначала прочитать соответствующие
локальные руководства в `node_modules/next/dist/docs/`.

Для данного документа 2026-09-17 выполнены lint, typecheck и npm test:
189 Vitest + 196 backend tests прошли. Это проверка текущей базы кода,
не реализация описанного API и не подтверждение Linux/CUDA-совместимости.

## Вне объёма

- Постоянно загруженная F5, несколько GPU-исполнителей, обучение моделей.
- Новый интерфейс выбора движков, новые голоса и изменение правил текста.
- Redis/Celery, метрики, админ-панели, стороннее объектное хранилище.
- Произвольные загружаемые референсы, callbacks и multi-tenant API.
- Обновление драйвера сервера и скрытая смена базового CUDA-образа.
- Реальное развёртывание или изменение исходников в рамках создания плана.
