# Каталог OSM, очередь текстов и локальные воркеры озвучки

Дата: 2026-09-16. Статус: первая рабочая вертикаль реализована; полный каталог,
массовые текстовые партии и административный интерфейс остаются следующими этапами.
Основание: `main` после `git pull --ff-only`, коммит `cd17c5a`.

## Результат

Сервер хранит каталог московских достопримечательностей, тексты, задания и готовое
аудио. Локальный компьютер сам забирает задания по HTTPS, синтезирует речь через
Silero или F5-TTS и загружает результат. Входящие подключения к домашнему компьютеру
не нужны. После выключения компьютера задания остаются на сервере; после запуска
воркер продолжает работу. Пользователь слушает сохранённый MP3 с сервера.

Поток: `OSM → places → text jobs → проверенный текст → audio jobs → локальный TTS
→ загрузка файла → проверка и публикация → плеер`.

Для первой версии: один сервер Node.js + SQLite на постоянном локальном диске,
один Python-воркер с одним активным синтезом, Silero как первый адаптер.
F5-TTS подключается через тот же интерфейс после выбора русскоязычных весов и
проверки качества. GPU сервера приложения не требуется. Redis, брокер сообщений,
публичный TTS endpoint и стриминг генерации для первой версии не нужны.

## Что уже есть и что потребуется изменить

- `backend/store.mjs`: SQLite WAL, задания и промежуточные результаты. Текущая
  очередь рассчитана на пользовательские истории: два активных задания, шесть
  новых в сутки по умолчанию, фактически последовательное выполнение.
- `backend/pipeline.mjs`: исследование, загрузка источников, проверка фактов,
  написание, редакторская проверка и синхронное ожидание озвучки.
- `backend/audio.mjs`: нормализация текста, TTS, FFmpeg, MP3 и кеш. Разделить
  синтез и обработку готового файла, чтобы принимать аудио удалённого воркера.
- `backend/server.mjs`: Node HTTP API, раздача MP3 с Range/HEAD. Текущий JSON parser
  и короткие HTTP timeouts не подходят для загрузок аудио; нужен отдельный handler.
- `backend/walk-discovery-catalog.mjs`: 2 129 зданий. Импорт требует адрес и здание,
  ограничивает координаты прямоугольником; он не охватывает все достопримечательности.
- `scripts/prod-db.mjs`: согласованный snapshot SQLite. При резервном копировании
  нового пайплайна учитывать и аудиофайлы, а не только базу.

Массовые задания хранить в отдельных таблицах той же серверной базы. Старый
`claimNext` и `recoverInterrupted` не должны захватывать или сбрасывать их.
Пользовательские квоты остаются отдельными от лимитов фоновых партий. Текущие
пользовательские истории и облачные TTS продолжают работать во время внедрения.

## 1. Каталог достопримечательностей Москвы

«Все» означает все подходящие объекты в конкретном снимке OSM по опубликованным
правилам отбора, а не гарантию полноты реальных достопримечательностей.

Сделать отдельный импорт PBF, переиспользовав опыт `scripts/build-walk-discovery.py`.
Зафиксировать дату, URL, checksum источника и версию правил. Проверять покрытие
PBF всей административной границы Москвы, включая Новую Москву; существующий
BBBike extract нельзя автоматически считать полным. Границу выбирать по проверенному
OSM relation ID, сохранять её версию. При недостаточном покрытии импорт не помечать полным.

Начальные правила: `historic=*` кроме `no`, `heritage=*` кроме `no`,
`tourism=attraction|museum|gallery|artwork|viewpoint|zoo|theme_park`,
именованные `leisure=park|garden`, а также исторически значимые здания с
Wikipedia/Wikidata/architect. Список правил версионировать; метаданные Wikidata сами
по себе не доказывают туристическую ценность объекта. Церкви и другие объекты
включать по этим признакам; спорные категории показывать в отчёте импорта.

Обрабатывать nodes, ways, multipolygon relations, объекты без почтового адреса.
Для площадных объектов выбирать точку на геометрии; она не считается входом или
подтверждением доступности. Не выполнять массовый reverse geocoding через Nominatim.

Хранить исходные OSM type/id, теги, геометрию/точку, название, адрес при наличии,
Wikipedia/Wikidata, timestamp и происхождение. Отдельно хранить внутренний `placeId`.
OSM ID задаёт точное совпадение; совпадение Wikidata, названия и геометрии даёт
кандидатов на объединение. Не объединять автоматически все объекты одной территории
или организации. Таблица aliases сохраняет все исходные объекты объединённого места.

Повторный импорт обновляет данные без повторных jobs для неизменных входов.
Удалённые объекты архивируются только после успешного полного снимка; неполный
импорт не удаляет прежний каталог. Хранить attribution «© OpenStreetMap contributors»,
ODbL и происхождение иных источников. Выводить количества по категориям, пропуски,
невалидную геометрию и возможные дубли.

## 2. Отдельные этапы текста и аудио

Создание партии принимает список `placeId` или снимок серверного фильтра,
лимит объектов, профиль текста, режим `text-only` или `text-and-audio`, профиль TTS.
Первый запуск — ограниченная партия; постановка тысяч jobs не означает одновременные
тысячи запросов. Есть pause/resume, отмена ожидающих задач, счётчики и явный retry.

Текстовый обработчик первоначально работает на сервере и использует существующего
провайдера исследования/написания. Сохраняет checkpoints после каждого этапа.
Переработать адресные prompts и validation под идентичность места: название,
OSM-данные, координаты, адрес если есть. Парк или памятник без номера дома должен
проходить обработку. Для карточки рассказывать о самом объекте; историю соседнего
дома нельзя автоматически использовать как его историю.

Сначала поддержать существующий формат рассказа 100–200 слов с проверяемыми
источниками. Более короткое описание — отдельный профиль с собственными лимитами
фактов/длины. Не ослаблять существующую проверку просто ради количества готовых текстов.
Сохранять `insufficient_evidence` и `review_required` как нормальные исходы.
Автоматическая проверка не обозначается как ручная редактура.

Утверждённая версия текста неизменяема: paragraphs, sources, facts, language,
content hash, версия генератора, время и способ проверки. Перед постановкой аудио
сервер получает и сохраняет `spokenText`, его hash и версию нормализатора.
Воркер синтезирует именно этот текст; модельное деление на фрагменты и правила
произношения входят в версию TTS-профиля. Текст доступен даже при выключенном TTS.

Озвучка имеет собственное задание и лимит попыток. Ошибка аудио не запускает
повторное исследование. Изменение текста/голоса создаёт новую версию аудио; ранее
опубликованный файл остаётся доступным до успешной замены. Провайдер не переключается
на платный облачный TTS автоматически при отсутствии локального воркера.

## 3. Хранение и состояния

Предлагаемые сущности:

| Таблица | Назначение |
| --- | --- |
| `osm_imports`, `places`, `place_osm_aliases` | Снимки, места и исходные идентификаторы |
| `content_batches`, `batch_items` | Неизменный состав партии и результаты её объектов |
| `place_texts` | Версии текста, факты, источники, результат проверки |
| `content_jobs` | Тип text/audio, входной snapshot, ключ дедупликации, состояние |
| `job_attempts` | История попыток, ошибки, worker ID, lease и heartbeat |
| `worker_credentials` | Хеши индивидуальных токенов, разрешённые профили, отзыв |
| `audio_artifacts` | Файл, checksum, размер, длительность и параметры синтеза |

Job содержит `id`, `kind`, `inputHash`, `profileVersion`, `priority`, `attempts`,
`maxAttempts`, `nextAttemptAt`, `leaseGeneration`, `leaseTokenHash`, `leaseExpiresAt`,
`workerId`, timestamps, checkpoints и нормализованную ошибку.

Состояния jobs: `queued → leased → succeeded`; временная ошибка/истечение lease:
`retry_wait → leased`; постоянная ошибка: `failed`. Дополнительно `cancelled`,
`review_required`, `insufficient_evidence` для соответствующих исходов.
Состояние полученного текста и доступность аудио не объединять в один флаг `ready`.

Уникальные ключи: текст — `placeId + входной content hash + язык + профиль/версия
генератора`; аудио — `textVersion + spokenTextHash + TTS profile version`.
Дата импорта сама по себе не инвалидирует неизменный текст. Партия ссылается на
существующее задание/артефакт при совпадении ключа.

Выдача задания транзакционная (`BEGIN IMMEDIATE`): выбрать подходящее доступное
задание, увеличить generation/attempt, закрепить worker и lease, затем commit.
Начальные настройки: lease 5 минут, heartbeat каждые 30 секунд, до 3 попыток,
повторы с задержками 30 секунд и 2 минуты с jitter. Часы сервера авторитетны.
Исчерпанные попытки переводятся в `failed`; ручной retry создаёт новую ограниченную
серию попыток с записью в журнале. Истечение lease обрабатывается и после рестарта.

## 4. API воркера: `/api/worker/v1`

Все методы требуют HTTPS и `Authorization: Bearer <worker-token>`. У каждого
устройства отдельный отзываемый токен, разрешающий только worker API и назначенные
TTS-профили. Это не `ADMIN_TOKEN`. Токены и lease tokens не пишутся в логи и URL.
Origin-проверки браузерной админки не применяются к машинным маршрутам; отдельная
проверка авторизации обязательна для каждого запроса. Редиректы с токенами запрещены.

| Метод | Вход | Результат |
| --- | --- | --- |
| `POST /claim` | `requestId`, `profileIds`, версия воркера | `200` с заданием или `204` и `Retry-After` |
| `POST /jobs/:id/heartbeat` | `leaseToken`, `leaseGeneration`, progress | `200` с новым сроком или `409 LEASE_LOST` |
| `PUT /jobs/:id/result` | binary WAV/MP3; lease headers, `X-Upload-Id`, `X-Content-SHA256` | `200` с сохранённым receipt после проверки/commit |
| `GET /jobs/:id` | Только авторизованный доступ владельца попытки | Состояние, generation, receipt; помогает после потери ответа |
| `POST /jobs/:id/fail` | lease, `failureId`, код и ограниченная диагностика | `200` с состоянием повтора/ошибки |

Claim возвращает `jobId`, `leaseToken`, `leaseGeneration`, `leaseExpiresAt`,
`textVersion`, `spokenText`, `spokenTextHash`, TTS-профиль и ограничения файла/длительности.
Профиль содержит engine, checksum весов, speaker/reference ID, language,
версию конфигурации и способ разбиения текста. Воркер не получает произвольную
команду shell, путь для записи или URL скачивания весов от задания.

Идемпотентность claim по `(worker credential, requestId)`: повтор после потери
ответа возвращает ту же действующую выдачу. После истечения — конфликт, затем новый
requestId; лимит активных lease на устройство не позволяет случайно забрать очередь.
Для повторной выдачи того же секрета lease использовать воспроизводимый HMAC от
job ID, generation и worker ID с серверным ключом вне базы; в базе хранить хеш.
Версию ключа сохранять с попыткой и поддерживать до завершения выданных lease.
Повтор fail с тем же `failureId` не увеличивает счётчик попыток.

Результаты принимаются только от текущего владельца с действующей generation и lease.
Проверять это перед загрузкой и повторно в транзакции публикации. Устаревший воркер
не может перезаписать результат новой попытки. После отмены или изменения целевой
версии старое задание также не может опубликовать результат.

Повтор успешного PUT с тем же upload ID и checksum возвращает сохранённый receipt,
даже если исходный lease уже завершён. Иные байты под тем же upload ID дают `409`.
Проверка точного ранее принятого receipt предшествует проверке активного lease.
`401/403` останавливают работу до исправления доступа, `409` прекращает попытку,
`413/422` обозначают невалидный результат, `429/503` дают ограниченный backoff.

## 5. Загрузка и публикация аудио

Для первой версии — один ограниченный binary upload, без base64 JSON и multipart
протокола возобновления. При обрыве повторяется загрузка готового локального файла,
а не синтез. Начальные пределы: 64 MiB входного файла, 300 секунд загрузки,
до 600 секунд входного аудио; допустимая длительность публикации задаётся профилем
текста, для существующих рассказов сохранить текущий диапазон 45–150 секунд.

Согласовать лимиты у Node, nginx и внешнего reverse proxy; увеличить timeout только
для upload-маршрута, ограничить число одновременных загрузок. Читать файл потоком
в временный каталог того же volume. Считать размер/hash на сервере, проверять
реальный формат и длительность через ffprobe, а не доверять MIME и метаданным клиента.
FFmpeg с ограничением времени и локальными файловыми протоколами приводит файл к
формату приложения. Heartbeat продолжает работать во время upload/обработки.

Порядок публикации: проверить → получить конечный MP3 и его hash → атомарно
переименовать → транзакционно проверить lease/версию и сохранить artifact + success
+ receipt. Не отмечать job завершённым до появления файла. Файловая система и SQLite
не имеют общей транзакции: сбой после rename допускает осиротевший файл; сборщик
удаляет только давно неиспользуемые файлы, учитывая незавершённые публикации.

Хранить upload checksum отдельно от checksum конечного MP3. Отдавать конечный MP3
по существующему `/api/story-audio/<sha256>.mp3` с Range/HEAD и immutable cache.
Начальное хранилище — `/data/audio` в постоянном volume; S3 можно добавить позже.
Бэкап должен сохранять все файлы, на которые ссылается snapshot базы. Проверять
доступное место до приёма файла; нехватка места не должна превращаться в success.

## 6. Локальный Python-воркер

Предлагаемая директория: `workers/tts/`, отдельные зависимости и инструкция запуска.
Интерфейс адаптера: `load(profile)` и `synthesize(spoken_text, output_path)`.
Сначала Silero; F5-TTS — второй адаптер без изменения серверного API.

На старте проверить модели, checksum, доступный CPU/GPU, выбранный профиль и
соединение с API. Модель загрузить один раз до claim; не занимать задания во время
скачивания весов. Версии Python/PyTorch/движка и образа фиксируются по результатам
проверки на целевой машине. Конкретный объём VRAM не обещать до выбора checkpoint.

Цикл: claim → сохранить локальный manifest → heartbeat в отдельном потоке →
разбить текст → синтезировать WAV → загрузить → сохранить receipt → очистить spool.
При пустой очереди опрашивать примерно раз в 10 секунд с jitter; ошибки сети дают
backoff до 60 секунд. Начальная concurrency — 1, сервер дополнительно ограничивает её.

Spool хранит job ID, generation, input hash, путь/хеш результата и upload ID,
с правами только владельцу. После рестарта сверить статус с сервером. Готовый файл
повторно отправляется только при действующем lease либо новой разрешённой выдаче
с тем же входом; утраченный lease не позволяет самовольно закончить старое задание.
После сетевого разделения попытаться продлить lease; при отказе остановить работу.

Синтезировать по предложениям в пределах лимитов модели; сохранять порядок,
использовать постоянный голос и заданные паузы. Нормализация громкости выполняется
сервером один раз. Для F5 сохранять ID/hash reference audio и его расшифровки;
референсы устанавливать отдельно, не принимать произвольные пути из jobs.
Проверить лицензию выбранных весов и права на образец голоса до массового выпуска.

Предлагаемые настройки, ещё не существующие: `WORKER_API_URL`, `WORKER_TOKEN`,
`WORKER_PROFILE_ID`, `WORKER_DEVICE`, `WORKER_SPOOL_DIR`, `WORKER_CONCURRENCY=1`.
Токен хранить локально вне Git. Веса и аудио также исключить из Git.

## 7. Управление и интеграция приложения

Админские операции: создать партию, просмотреть состав/прогресс, поставить на паузу,
отменить, повторить конкретные ошибки, утвердить текст, заказать озвучку другим
профилем, выпустить/отозвать токен воркера. В MVP достаточно CLI и API; затем экран
админки с теми же операциями. Операции создания партий также идемпотентны.

Pause блокирует новые выдачи, текущие могут закончиться. Cancel инвалидирует lease;
новый текст делает прежнее ожидающее аудиозадание неактуальным. Ошибка одного объекта
не останавливает всю партию. Отдельно показывать отсутствие подходящего online-воркера.

Метрики: queued/leased/succeeded по этапам, задержка очереди, скорость синтеза,
последний heartbeat, ошибки, расход API на тексты, занятый диск. Не логировать ключи,
полные тексты источников или voice reference. Ограничивать число text jobs в работе,
число запусков в сутки и токены на запрос; денежный лимит нельзя объявлять строгим
без надёжных цен и учёта уже выполняющихся вызовов.

Для нового каталога добавить read API карточек с раздельными полями text/audio status
и связью по `placeId`; карта показывает текст до озвучки и готовое аудио после неё.
Не создавать фиктивный почтовый адрес для памятника ради старого address API.
Адаптировать типы/админку к профилям Silero/F5, не пропускать их через список голосов
OpenAI/Яндекса. Старые endpoints и уже опубликованные истории сохраняют контракт.

## 8. Последовательность реализации и критерии готовности

1. **Вертикальный прототип очереди.** Миграции, токены, claim/heartbeat/fail,
   загрузка и публикация файла, Python-воркер с тестовым адаптером. Один подготовленный
   текст превращается в доступное на сервере аудио; GPU ещё не обязателен.
2. **Реальный Silero.** Закреплённые веса, разбиение текста, spool, restart/retry,
   запуск на целевой машине. Сравнить несколько историй с именами, датами и адресами;
   измерить время синтеза и память. Проверить фактическое прослушивание результата.
3. **Разделение существующего пайплайна.** Text-only checkpoints, отдельное audio job,
   неизменные версии текстов и профили, доступность текста без аудио. Проверить
   существующие адресные истории, walk research, ручную редактуру и переозвучку.
4. **Полный импорт OSM и партии.** Границы/покрытие, объекты без адресов, дедупликация,
   отчёт импорта, адаптация исследования под place identity, ограничения обработки.
5. **Каталог в приложении и эксплуатация.** Read API, карточки/аудио, админские статусы,
   monitoring, бэкап/восстановление, документация сервера и локального запуска.
6. **Пилот и массовый запуск.** Партия 50 разных объектов, включая парки и памятники
   без адреса. Проверить факты/ударения/обрывы, стоимость текста и скорость обработки.
   Затем партии всего снимка по настроенному бюджету. F5 добавлять после пилота,
   если качество/нужный голос оправдывают отдельную модель.

В реализации ожидаются новые модули `backend/content-store.mjs`,
`backend/worker-api.mjs`, `backend/audio-ingest.mjs`, `backend/content-batches.mjs`,
скрипт импорта OSM, `workers/tts/` и миграции. Имена предварительные; общие примитивы
исследования/проверки извлекать из текущего pipeline без копирования всей цепочки.
Перед изменением Next.js-кода установить зависимости и прочитать соответствующие
локальные руководства `node_modules/next/dist/docs/`, как требует AGENTS.md.

## 9. Проверки

- Два независимых соединения/воркера одновременно пытаются забрать одно задание;
  действующий lease получает один. Heartbeat, expiry и restart проверяются с
  управляемыми часами, без долгих реальных ожиданий.
- Потеря ответа на claim/PUT/fail не создаёт дублей. Просроченный воркер,
  отозванный токен, отменённая задача и старая версия текста не публикуют результат.
- Обрыв загрузки, неверный hash, слишком большой/повреждённый файл, timeout FFmpeg,
  нехватка диска и сбой между rename/commit оставляют восстанавливаемое состояние.
- Повтор TTS не вызывает исследование; restart text processor продолжает checkpoints.
  Сбой после внешнего платного ответа до checkpoint может повторить расход: гарантии
  exactly-once для внешнего провайдера нет. Семантика очереди — at-least-once,
  публикация идемпотентна.
- Импорт включает node/way/relation и места без адреса, исключает объекты вне границы,
  сохраняет происхождение; повтор полного снимка не создаёт jobs, неполный не архивирует.
- End-to-end: импорт fixture → текст с тестовым провайдером → внешний воркер →
  настоящий валидный аудиофайл → upload → MP3 → Range/HEAD → восстановление из бэкапа.
- Регрессии: `pnpm test`, `pnpm lint`, `pnpm typecheck`, `pnpm build` при изменениях
  приложения; Python-тесты воркера; интеграционные проверки FFmpeg и reverse proxy.
  Оплачиваемые API и массовая озвучка не входят в автоматические unit-тесты.

## Решения, необходимые перед настройкой реальной машины

Уточнить ОС/CPU/GPU/VRAM, место для весов/spool, адрес сервера и первый русский
голос. Это не блокирует очередь/API и тестовый воркер. Окончательные зависимости,
checkpoint Silero/F5 и скорость обработки фиксируются после проверки оборудования.
Этот план не запускает генерацию, не изменяет production и не загружает модели.
