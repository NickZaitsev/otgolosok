# План: надёжный поиск источников и генерация текста без обязательного JSON

Status: plan, 2026-09-18.

> Для агента: это снимок решений и кода на дату создания. Перед реализацией проверь факты по актуальному коду. Документ написан по-русски согласно пользовательским правилам репозитория; реализацию выполнять через `implement-plan`.

## Контекст

Пользователь сообщает о плохом поиске и частых невалидных JSON-ответах при генерации историй. Сейчас модель обязана выдавать JSON на каждом этапе: поиск, извлечение фактов, написание и редакторская проверка. Однако поиск уже возвращает URL через инструмент, а итог для слушателя — обычный текст. JSON рассказа нужен приложению для хранения абзацев и подтверждений; создавать эту оболочку должен код.

Есть два исполнения: массовые задания OSM в `backend/content-pipeline.mjs` и адресные истории в `backend/pipeline.mjs`. Второе используется также исследованием прогулок. Общий адаптер `backend/provider.mjs` отправляет `POST ${OPENAI_BASE_URL}/responses`; поиск включается через `web_search`. Конкретный провайдер задаётся окружением. Его поддержка принудительного поиска и схем ответов не проверена в рамках подготовки плана: совместимый маршрут `/responses` сам по себе её не гарантирует. Тарифы из кода неизвестны; новый поисковый сервис не подключаем.

Цель: перестать терять пригодные ответы из-за сериализации, находить доступные материалы о правильном объекте, писать соразмерно найденному материалу и сохранять проверку утверждений. Увеличение числа готовых текстов не должно достигаться публикацией неподтверждённых историй.

## Согласованные решения

1. Пользователь разрешил один источник и делегировал выбор порога фактов, охвата и остальных деталей. Удалить требование двух издателей и минимальную квоту пяти/трёх фактов. Требовать подтверждённую идентичность места и хотя бы одно содержательное утверждение об архитектуре или истории; одно название или адрес не считаются историей.
2. Поиск, написание и переписывание рассказа возвращают обычный текст. URL поиска берём из метаданных инструмента. Сохраняем ограниченную машинную структуру для доказательств и решения редактора: без неё автоматическая публикация и связи с источниками стали бы менее надёжными. JSON API и SQLite остаётся обычным форматом приложения.
3. Исправить оба исполнения через общие функции исследования и подготовки текста; сохранить отдельные очереди, права, квоты и жизненные циклы. Исследование прогулок получает исправления через адресный путь.
4. Один доступный содержательный источник может быть достаточен и для описания, и для рассказа. Предпочитать учреждение, музей, архив, наследие и редакционные краеведческие материалы; авторитетность не определяется одним доменным именем. Поисковый сниппет, агрегатор или рекламная карточка сами по себе недостаточны. Второй источник нужен при конкретном пробеле или противоречии, а не для заполнения квоты.
5. Не вводить новую квоту фактов взамен старой. Длину выбирать по материалу: описание — ориентир 50–100 слов, допустимо 20–100; рассказ — ориентир 100–200, допустимо 100–250. Для рассказа нижняя граница сохраняет действующий контракт озвучки; при нехватке материала не растягивать текст и не выдавать короткое описание за рассказ. Автоматическое переключение профиля и озвучка коротких описаний не входят в эту работу.
6. Сохранить проверку цитат по загруженной странице, различение выбранного здания/бывшего здания/соседнего места, редакционную проверку утверждений и существующий режим ручного либо автоматического утверждения. Наличие цитаты доказывает происхождение утверждения, но не абсолютную истинность источника.
7. Сохранить текущие модели и настройки публикации. Новых платных интеграций, самостоятельного запуска массовых партий и новой панели наблюдения не добавлять. Структурированные этапы должны иметь ограниченную обработку ошибок, а не бесконечные исправления JSON.

## Проверенные факты кодовой базы

- `backend/provider.mjs:42–59`: `response()` всегда вызывает `parseModelJson(output)`, в том числе при поиске. В запросе нет ограничения формы ответа схемой; URL уже извлекаются из annotations и `web_search_call.action`. Отсутствие вызова поиска приводит к `NO_SEARCH_EVIDENCE`.
- `backend/domain.mjs:23`: `parseModelJson()` принимает объект JSON, допускает Markdown fence и отвергает прочий текст. `INVALID_MODEL_OUTPUT` возникает до возврата результата в пайплайн.
- `backend/content-pipeline.mjs:57–58`: первый вызов автора находится до блока, обрабатывающего `INVALID_DRAFT`. Синтаксическая ошибка JSON не попадает в исправление черновика. В `backend/pipeline.mjs` `acceptDraft()` тоже получает уже разобранный объект.
- `backend/content-pipeline.mjs:40–53`: `sourcesFrom()` пересекает URL из модельного JSON с URL инструмента без общей канонизации; рассматриваются первые пять элементов. После загрузки меньше двух издателей означает отказ без дополнительного поиска.
- `backend/pipeline.mjs:10–28, 97–122`: адресный путь удаляет fragment и `utm_*`, умеет один дополнительный поиск после неудачной загрузки страниц. Поиск не повторяется для конкретных пробелов в доказательствах.
- `backend/domain.mjs:62–92`: `validateFacts()` требует пять фактов и двух издателей, проверяет принадлежность цитат тексту, поддерживает до восьми фактов и три цитаты на факт. Проверка не устанавливает логическое следование утверждения из цитаты — это задача редактора.
- `backend/domain.mjs:96`: `validateDraft()` требует минимум пять использованных `factIds`, 2–6 абзацев и 100–250 слов. `draftPrompt()` просит 3–5 абзацев и 100–200 слов. Описание в `content-pipeline.mjs` требует три использованных факта, но предварительная проверка всё равно требует пять.
- `backend/source-text.mjs:15`: HTML/PDF ограничиваются первыми 14 000 символами. `pageText()` дополнительно обрезает HTML до 22 000 символов. Полезный фрагмент длинного документа может не попасть в контекст. В `researchPrompt()` PDF всё ещё запрещены, хотя загрузка и извлечение PDF уже реализованы.
- `backend/safe-fetch.mjs`: есть ограничения размера, времени, redirect, DNS/IP и типов содержимого. Статусы HTTP сводятся к `BAD_STATUS`, поэтому сейчас нельзя надёжно отличить 404 от временного 503 для повторов.
- `backend/content-store.mjs:139–143`: ключ задания включает место, hash данных и профиль, но не версию пайплайна. Колонка `profile_version` существует, записывается как `1` и не возвращается `claimContentJob()`. `retryBatchItem()` сохраняет checkpoint; `failContentJob()` повторяет любой `failed`, независимо от временности причины.
- `backend/domain.mjs:3, 19`, `backend/walk-research-store.mjs:64`: адресные ключи и кеш исследования используют `PIPELINE_VERSION` через `addressKey()`.
- `src/features/generator/types.ts`, `story-generator.tsx:173`: публичный рассказ содержит абзацы, `factIds`, источники и факты; UI показывает подтверждения. `backend/admin.mjs:25, 52` повторно проверяет редакторские тексты и имеет собственные ограничения длины.
- `backend/audio.mjs:9` и профиль внешней озвучки в `backend/store.mjs` предполагают рассказ длительностью 45–150 секунд. `createBatch()` запрещает `description-v1` в режиме `text-and-audio`.
- Скрипты проверок: `pnpm lint`, `pnpm typecheck`, `pnpm test` (Vitest и backend Node tests). `package.json` требует Node >=24.20.0; при подготовке плана локально обнаружен Node 24.18.0. Это ограничение среды, а не основание понижать требование проекта.

## Реализация

### 0. Воспроизвести ошибки до изменения поведения

Обновить `backend/provider.test.mjs`, `backend/content-pipeline.test.mjs`, `backend/pipeline.test.mjs`. Добавить интеграцию настоящего `createProvider()` с подменённым HTTP, а не только mock `response()`, возвращающий готовые объекты.

Зафиксировать: пригодный текст с кавычками/переносами сейчас отвергается как JSON; ссылки инструмента теряются при невалидном поисковом JSON; массовый поиск не восстанавливается после недоступных страниц; один источник и меньше пяти содержательных фактов отвергаются. Проверять итоговый текст, подтверждения, состояние и отсутствие преждевременной публикации/озвучки.

### 1. Разделить транспорт, текст и структурированные ответы

Изменить `backend/provider.mjs`, добавить `backend/model-output.mjs` и его тесты.

- `provider.response(prompt, {search, signal, timeoutMs, maxTokens, model, ...})` возвращает транспортный результат `{text, sources, usage, model}`. `sources` — ограниченный список `{url, title?, origin}` из подтверждённых типов метаданных инструмента/цитат; это кандидаты, а не доказательства прочитанной страницы. Обычный ответ не проходит `parseModelJson()`.
- Сохранить обработку JSON/SSE транспортного конверта, ограничение размера и проверку завершённости. Различать отказ модели, обрыв по лимиту, пустой ответ, отсутствие поискового вызова, некорректный транспорт и ошибку структурированного содержимого. Не принимать незавершённый текст за готовый рассказ.
- `requestStructured(provider, prompt, {schemaName, validate, signal, ...})` нужен только извлечению доказательств и проверке. Результат проходит локальную проверку формы и доменных ограничений. Если настроенный провайдер документированно поддерживает строгую схему, использовать её только на этих вызовах; проверить реальную совместимость до включения. Не предполагать поддержку по имени модели или URL и не делать скрытых платных проб при каждом задании.
- Без поддержки схем использовать JSON-инструкцию только на этих двух этапах, локальную валидацию и не более одного исправления формы. Передать краткие ошибки и необходимые исходные данные; не «лечить» JSON regex-заменами кавычек, не угадывать пропущенные поля и не превращать ошибку в approval. Повторная ошибка остаётся отдельной диагностируемой причиной.
- Возвращать/учитывать `usage` до доменного разбора, включая отвергнутые ответы. Не суммировать `input_tokens + output_tokens + total_tokens` как три независимых расхода. Использовать `total_tokens`, иначе сумму входа и выхода.
- Обновить оба потребителя одновременно. Удалить неиспользуемые допущения о `result.value`; JSON приложения формируется в коде.

### 2. Сделать единое исследование с ограниченным дополнительным поиском

Создать `backend/research.mjs`, `backend/research.test.mjs`; изменить `backend/prompts.mjs`, `backend/source-text.mjs`, `backend/safe-fetch.mjs` и соответствующие тесты.

Контракт: `researchPlace({place, address, profile}, {provider, fetchPage, checkpoint, saveCheckpoint, signal})` возвращает проверенный материал для автора. `place` необязателен для адресного пути. Сохранение состояния передаётся адаптером существующей очереди.

1. Использовать точное имя, адрес/строение, координаты и имеющиеся OSM-идентификаторы. Валидный OSM `wikipedia` может дать прямого кандидата страницы; сохранять происхождение кандидата отдельно от web-search. Wikidata использовать как подсказку идентичности без новой интеграции. Все URL проходят существующий безопасный fetch.
2. Поисковый prompt просит найти материалы и кратко описать, что найдено обычным текстом. URL брать из инструмента, не извлекать доверенные адреса из свободного текста. Требовать факт выполнения поиска; не полагаться только на просьбу модели. Если принудительный вызов поддерживается адаптером, применить его после проверки совместимости.
3. Общая канонизация убирает fragment и tracking `utm_*`, сохраняет значимые параметры, различия путей и языка. Сначала нормализовать и убрать дубли, потом ограничить количество. После redirect повторно убрать дубли по конечному адресу. Не считать разные субдомены независимыми доказательствами.
4. Первый проход: до пяти кандидатов. Второй, максимум один, нужен при недоступности, ошибке идентичности, недостатке содержательного материала или неразрешённом противоречии. Запросить конкретный пробел и исключить уже неудачные URL; искать историческое имя/официальное учреждение при наличии таких сведений. Не заменять объект одноимённым местом или целым районом.
5. Общий лимит — два поисковых ответа, до десяти уникальных загрузок и до двух проходов извлечения доказательств. Загружать максимум три страницы одновременно. Начать с существующего общего срока 600 секунд; каждый вызов получает оставшееся время. Не пытаться уложить бесконечные поисковые действия в словесную просьбу: ограничивать вызовы приложения и использовать лимит tool calls провайдера только при подтверждённой поддержке.
6. Сохранять удачные загрузки и ошибки кандидатов по мере завершения, а не после успеха всей группы. При продолжении не скачивать заново готовые страницы. Отмена и общий deadline прекращают работу, а не превращаются в «материалов нет».
7. Разрешить PDF в поисковых prompts. В `source-text.mjs` извлекать ограниченный текстовый корпус (например, максимум 80 000 символов/30 страниц PDF), затем выбирать релевантные непрерывные блоки до общего бюджета 14 000 символов на источник по имени, адресу и предмету поиска. Это не LLM-вызов. Не склеивать удалённые предложения в одну «точную цитату»; доказательства проверять внутри сохранённых блоков. Избежать предварительной обрезки HTML в `pageText()`, мешающей отбору. Сохранять ограничения байтов, времени и очистку PDF-ресурсов.

Тексты страниц и метаданные — недоверенные данные, не инструкции. Сохранить защиту SSRF, ограничения redirect/размера и запрет использовать сниппет вместо страницы. Причина исключения источника должна быть различима: недоступен, пуст, не тот объект, не содержит нужного материала.

### 3. Убрать числовые квоты фактов, сохранить доказательства

Изменить `backend/domain.mjs`, `backend/prompts.mjs`; добавить `backend/content-policy.mjs` с общей политикой профилей и тестами. Сигнатура `validateFacts(result, sources, {requireEditorialScope, policyVersion})`; новую политику выбирать явно, старые данные не трактовать молча по новым правилам.

- Извлекать до восьми содержательных утверждений, столько, сколько подтверждено. Не просить выдумывать пять пунктов из одной мысли. Один источник и один содержательный факт допустимы; отсутствие фактов, неустановленная идентичность и рекламная информация недостаточны.
- Сохранить `claim`, `topic`, `scope`, `location`, доказательства `{sourceId, quote}` и пространственные ограничения для соседних мест. Вынести назначение `f1…f8` в код, чтобы модель не отвечала за уникальность внутренних ID. Возвращать данные идентичности отдельно от художественного текста.
- Проверять источник и каждый цитируемый непрерывный фрагмент. Неизвестные sourceId, выдуманные цитаты и неподтверждённые расстояния не учитываются. Не вычислять качество текста по количеству оставшихся пунктов.
- Конфликтующие даты/атрибуции исключать или уточнять вторым поиском; не выбирать удобную версию молча. Редактор оценивает, достаточно ли материала для осмысленного текста и действительно ли цитаты поддерживают утверждения.
- Профили задают единые пределы текста для prompts, валидаторов и редакторского интерфейса. Максимальные ограничения остаются техническими; целевая длина не должна приводить к повторам. Для описания 1–3 абзаца, для рассказа 2–6.

### 4. Автор пишет текст; приложение собирает рассказ

Создать `backend/story-writing.mjs` и тесты; изменить `backend/prompts.mjs`, удалить дубли `writingPrompt`, `repairPrompt`, `reviewRepairPrompt` из `backend/content-pipeline.mjs`.

- `writeStory(evidence, {profile, provider, checkpoint, saveCheckpoint, signal})` просит только русский рассказ с пустыми строками между абзацами. Никаких JSON, factIds, заголовков, ссылок и служебных маркеров в ответе автора. Переписывание имеет тот же контракт.
- `parseStoryText(text, {profile})` нормализует CRLF и пустые строки, проверяет непустоту, объём и число абзацев. Не разбивает текст по предложениям и не выполняет эвристический JSON-repair. Очевидную служебную оболочку/отказ не публикует; допускается одно исправление по конкретной причине, а не за несовпадение с желаемым числом слов.
- Заголовок берётся из установленного `evidence.placeName`; отдельный LLM-вызов и специальный синтаксис первой строки не нужны. Объект `{title, address, paragraphs, wordCount, ...}` формирует код.
- Проверяющему передать абзацы с назначенными кодом индексами, доказательства и цитаты. Он возвращает компактное `{approved, issues, paragraphFacts}`; `paragraphFacts` содержит индекс абзаца и список поддерживающих factIds. Это позволяет сохранить публичный контракт и показать реальные подтверждения, не заставляя автора размечать прозу.
- Проверять все индексы и ID, полноту покрытия абзацев, отсутствие дубликатов/противоречия между `approved` и `issues`. Проверяющий должен проверять каждое утверждение, а не просто отметить наличие факта в абзаце. Не приписывать всем абзацам все факты автоматически. После изменения текста прежняя проверка недействительна.
- Не более одного содержательного переписывания и повторной проверки на подготовку текста; счётчик сохраняется в checkpoint. Ошибки формы структурированного ответа обрабатываются отдельно согласно шагу 1, но тоже входят в общий deadline. Повторное отклонение — `review_required`; технический сбой проверки не означает одобрение.
- Собрать `paragraphs[].factIds`, опубликованные `facts` и использованные `sources` из принятой проверки. До её успеха результат остаётся черновиком; признаки `verification: automatic`, публикация и озвучка появляются только после принятия.

### 5. Объединить исполнение и корректно продолжать задания

Изменить `backend/content-pipeline.mjs`, `backend/pipeline.mjs`, `backend/content-store.mjs`, `backend/store.mjs`, `backend/walk-research-store.mjs`, `backend/admin.mjs` и их тесты.

- Оба пайплайна вызывают общие `researchPlace()` и `writeStory()`, передавая собственный способ сохранения. Сохранить `researchOnly` для прогулок, редакторское утверждение и существующий путь озвучки уже принятого текста.
- В checkpoint явно хранить версию, кандидатов и результаты загрузки, проверенные доказательства, текст черновика, hash проверенного текста, решение редактора и использованные попытки. Сохранять только ограниченные данные для объяснения ошибки: этап, код, HTTP status, число попыток, расход, время. Не сохранять ключи, Authorization, сырые ответы провайдера или URL с секретными параметрами в диагностику.
- Версионировать адресный кеш через `PIPELINE_VERSION`, массовый input key — через версию пайплайна/профиля. Возвращать версию из `claimContentJob()`. Новое задание не должно повторно использовать старый неудачный результат только из-за совпадения места и профиля.
- Готовые опубликованные тексты, аудио и ручные правки сохраняются. Для незавершённых старых checkpoint сделать явный адаптер: переносить безопасные URL и загруженные тексты; доказательства повторно проверить; legacy draft либо перевести в обычный текст и проверить заново, либо отбросить только этот этап. Не очищать всю базу и не запускать новые платные задания миграцией.
- При пользовательском retry с плохим набором источников разрешить новый ограниченный раунд исследования; при временном сбое продолжить с сохранённого этапа. Отдельно учитывать число запросов в попытке и общий лимит автоматических попыток. Не обнулять счётчики редакторских исправлений при каждом перезапуске процесса.
- `editorialDraft()` и `hasValidStoryText()` должны учитывать версию политики, сохраняя возможность редактировать старые материалы. Публичные `GeneratedStory` и формат озвучки остаются совместимыми. Если затронут UI, сначала прочитать соответствующие руководства в `node_modules/next/dist/docs/`.

### 6. Повторы только для временных ошибок

Изменить `backend/provider.mjs`, `backend/safe-fetch.mjs`, `backend/content-store.mjs`, `backend/pipeline.mjs`; общую небольшую функцию повторов при необходимости вынести в `backend/retry.mjs` с тестами.

- Сохранять безопасный HTTP status и ограниченный `Retry-After` без тела ответа в ошибке на транспортной границе. Повторять network/timeout, 429 и 5xx: максимум две повторные попытки с задержками 1 и 2 секунды, jitter и верхней границей `Retry-After` 10 секунд. Каждый повтор ограничен оставшимся deadline; отмена и истечение общего срока не повторяются.
- 400/401/403/404, отказ модели, неверная схема запроса и некорректная конфигурация не получают транспортные повторы. Ошибка формы ответа имеет отдельный единственный repair, описанный выше. Недостаток материалов — результат исследования, а не временный сбой.
- После исчерпания транспортных повторов массовая очередь может использовать существующие отложенные попытки 30/120 секунд и максимум три попытки задания. `failContentJob()` должен учитывать retryable-класс, не повторять все `failed`. Учесть совокупную верхнюю границу вызовов и повторов; внешние повторы не начинают исследование с нуля при сохранённом успехе.
- Сохранить хорошие источники при сбое одного сайта. Если все источники недоступны временно, возвращать техническую ошибку, а не `insufficient_evidence`. Объяснять ошибки русским текстом существующего API без вывода сырых ответов.

## Тестирование и проверка

Новые тесты работают на локальных фикстурах, без платных API. Сначала воспроизвести дефект, затем менять код.

1. Адаптер: обычная проза, кавычки/переносы, транспорт JSON/SSE, отказ/обрыв/пустой ответ; источники инструмента при свободном ответе; структурированная ошибка, одно исправление и окончательный отказ; схема не заменяет доменную проверку; расход учитывается без двойного сложения.
2. Поиск: единственный качественный источник; только сниппет; один содержательный факт; только адрес; чужое строение; место без адреса; дубли/redirect/utm; первый набор недоступен, второй пригоден; пробел или конфликт в фактах; временно недоступны все сайты. Проверить URL-бюджет, отсутствие лишнего второго поиска и сохранение результатов загрузки при продолжении.
3. Извлечение: материал после первых 14 000 символов HTML/PDF, лимит страниц/байтов/времени, отсутствие склейки цитат из удалённых блоков, недоверенные инструкции в странице. Сохранить все проверки SSRF и DNS/redirect.
4. Текст: пределы описания 19/20/100/101 слов, рассказа 99/100/250/251, число абзацев, отсутствие квоты factIds; связи назначаются принятой проверкой; неизвестный ID/индекс, отсутствие покрытия, ложное approval, новая дата без доказательства и неоднозначный соседний объект не публикуются. Проверить однократное переписывание и последующее отклонение без TTS.
5. Очередь: временные/постоянные ошибки, отмена во время backoff, лимит попыток, восстановление после остановки процесса, старые checkpoint и версии ключей. Подтвердить, что готовый текст при повторе озвучки не вызывает поиск/автора/редактора и ручные правки не теряются.
6. Сквозная локальная проверка через HTTP API с настоящим адаптером и подменёнными внешними HTTP/TTS: партия → очередь → источник → текст → проверка → публикация; отдельно ручное утверждение и отказ. Адресное исследование/прогулка должно продолжить работу с тем же публичным контрактом. В опубликованном тексте нет JSON и служебных ID, список источников соответствует подтверждениям.
7. Перед каждым коммитом: `pnpm lint`, `pnpm typecheck`, `pnpm test`; для всей реализации также `pnpm build`. Использовать поддерживаемую проектом версию Node. Проверки без реальных внешних услуг; не исправлять сторонние пользовательские изменения ради чистого дерева.

Для оценки качества создать `scripts/evaluate-text-pipeline.mjs` и небольшой обезличенный набор локальных фикстур: известное здание, малоизвестный памятник, парк без адреса, PDF, одноимённые объекты, плохие источники и отсутствие материала. Отчёт показывает причины отказов, точность идентификации по фикстуре, успешность сохранения текста, число вызовов, расход и длительность; это разовый инструмент, без новой инфраструктуры.

Критерии приёмки: ошибки синтаксиса JSON не могут возникнуть на этапе автора/поиска; все положительные фикстуры с одним источником и непустым подтверждённым материалом проходят при соблюдении профиля; все отрицательные не публикуются; бюджеты и checkpoint проверены; полная автоматическая проверка проходит. Достоверность исторических утверждений и качество живого поиска дополнительно оценить вручную на ограниченном пилоте после реализации. Реальные платные вызовы выполняются отдельно от тестов и массовой генерации; не заявлять улучшение живого поиска только на основании mock-тестов и не придумывать ожидаемый процент успеха.

Результаты проверки и реальные ограничения записать в `docs/agents/text-generation-verification.md`, добавить ссылку и описание из двух предложений в `docs/agents/README.md` (сейчас файла нет). При реализации обновить README по форматам, лимитам и причинам отказа. Делать атомарные коммиты в текущей ветке, без создания новой.
