# Создание редактора через CLI

`pnpm auth:set-editor EMAIL [ПУТЬ_К_БАЗЕ]` теперь создаёт отсутствующий аккаунт
Better Auth вместе с паролем и ролью `editor`. В production-образе модуль доступен
как `/app/editor-account.mjs`: Dockerfile уже копирует все backend-модули в `/app`.
Полная команда запуска приведена в README; обновлённый образ должен быть развёрнут
до первого использования команды на сервере.

Пароль запрашивается дважды со скрытым вводом либо поступает через stdin при
`--password-stdin`. В выводе нет пароля, хеша, токена сессии и необработанных ошибок
БД. Для существующего пользователя команда проверяет текущий пароль перед
назначением роли: публичная регистрация не подтверждает владение email, поэтому
одного совпадения адреса недостаточно. Смена пароля этой командой не предусмотрена.

Создание `user` и `account` выполняется одной транзакцией. Хеш формируется
`hashPassword` из `better-auth/crypto`; существующий пароль проверяется через
`verifyPassword`. После асинхронной проверки запись пользователя и хеш повторно
сверяются под SQLite `BEGIN IMMEDIATE`, чтобы исключить повышение прав по устаревшей
проверке. Команда требует существующую базу со схемой авторизации и не создаёт её
при опечатке в пути.

Проверка 21 сентября 2026 года: новый CLI-аккаунт прошёл вход через настоящий
`POST /api/auth/sign-in/email`, полученная cookie дала HTTP 200 на
`GET /api/story-admin/jobs`; без cookie получен 401. Тесты покрывают повторный
запуск, неверный пароль существующего пользователя, границы длины, атомарный откат
и конкурирующее создание. В отдельном PTY проверены скрытый ввод, несовпадение
паролей, Ctrl+C и EOF; введённый пароль не попал в вывод.

При диагностике production в этот день рабочая `/data/auth.sqlite` была пустой,
а `ALLOW_LEGACY_ADMIN_TOKEN` выключен. Это объясняло отсутствие доступа редактора
после перехода на email и пароль; изменение CLI само по себе не создаёт аккаунт
на production и не включает старый механизм входа.
